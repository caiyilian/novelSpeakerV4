## 0. 本次范围与一条既定决策

用户决定：**不再补测 `deepseek-v4-pro` / `glm-5.2` / `kimi-k3`**。理由是这几个模型的 TPM 限制同样偏高，实际运行中会频繁被限流，反而拖慢整体进度，与 6.7/6.8 Flash Lite 遇到的问题是同一类。**`deepseek-v4-flash` 已是当前最合适的执行模型**，模型维度不再横向铺开。

因此本轮把力量全部投向三件事：把 98% 缺口拆清楚、把评测基建固定下来、把可复用的外部方案查明白。

## 1. 「非人物发声」口径重建实验

### 1.1 第一层事实：基线几乎从不输出这个标签

统计五卷基线原始输出的标签分布：

| 卷 | 输出「非人物发声」次数 | 输出「旁白」次数 | 该卷引语总数 |
| --- | ---: | ---: | ---: |
| 1 | 0 | 0 | 1349 |
| 2 | 0 | 0 | 1425 |
| 3 | 0 | 0 | 1215 |
| 4 | 3 | 0 | 1561 |
| 5 | **0** | 0 | 1459 |

**7009 条里只输出了 3 次。** 第 5 卷甚至加了一版把规则和四类例子都写清楚的 v2 提示词，结果依然是 0 次。

而答案中属于非人物类的引语共 **280 条**（字面「非人物发声」226 条 + 「旁白」54 条，评分器把「旁白」也归一为「非人物发声」）。也就是说这一类**基线一条都没拿到**。

### 1.2 第二层事实：拆成独立任务后，模型立刻就会了

把"这是不是一句真实发言"从"这是谁说的"里拆出来单独问（输入全卷正文 + 引语编号，只输出 A/B）：

| 配置 | 非人物召回率 | 精确率 | 判为非人物的次数 | 耗时 | reasoning token |
| --- | ---: | ---: | ---: | ---: | ---: |
| 基础提示词 + 关推理 | 49.38% | 44.44% | 90 | 37s | 0 |
| 少样本示例 + 关推理 | 64.20% | 47.71% | 109 | 36s | 0 |
| **少样本示例 + 高推理** | **91.36%** | 49.33% | 150 | 288s | 45356 |

**召回率从联合任务里的 0% 变成 91.36%。**

这证明了一件重要的事：模型**具备**区分"引号是真实发言"与"引号是引用/神态/强调"的能力。它在联合任务里得 0，不是能力不足，而是**行为问题**——当被要求"为每一处引号对话标注说话人"时，它默认每一处引号都必须有一个说话人，于是永远不会去用那个"没有人"的标签。

**任务分解改变了模型的行为，而提示词工程改变不了。** 这与第一轮"细化提示词只涨 1.17pp"的结论互相印证。

### 1.3 第三层事实：误报暴露了标注本身的边界歧义

拆出任务后精确率只有约 49%，即把 76 条真实对话误判成"非发言"。逐条看误报，原因不是模型乱猜：

```
L90:  罗伦斯别开视线心想：「就算你这样看我，我也没辄。」       答案=罗伦斯
L132: 罗伦斯心想：「赫萝还真是玩不腻。」                     答案=罗伦斯
L175: 「……」                                              答案=赫萝
L216: 心想：「早知道就不该太宠赫萝」的罗伦斯……               答案=罗伦斯
```

这些是**内心独白**。按自然阅读，它们确实"不是当场说出口的话"；但答案把它们归给了角色本人。

进一步统计：答案中所有"同一行带「心想／暗想／心中／思忖／喃喃」"的引语共 81 条——

| 答案标签 | 条数 |
| --- | ---: |
| 归属给具体人物 | **67** |
| 标为非人物发声 | **14** |

**同一个表面模式（`X 心想：「……」`），答案自身就有约 17% 的分歧。**

### 1.4 这一节的结论

「非人物发声」这一类错误要拆成两个性质完全不同的问题：

| 问题 | 条数量级 | 性质 | 可解性 |
| --- | ---: | --- | --- |
| 模型根本不输出该标签 | 246（基线侧） | **行为问题** | 已证明可解：任务分解后召回 91% |
| 内心独白该归人物还是该标非人物 | 81 条涉及 | **标注边界问题** | 需要先固化规范，不能靠模型猜 |
| 短引语（≤2 字，如「又」） | 64 条 | 判断可判定 | 可解 |

**因此，把这一项算作"6 个百分点差距"的一部分是不公平的**——其中相当一部分是评测口径本身没有固定下来。这与原复盘文档第 6 节第 9 条（"保留争议清单，不应自动扩大答案来迎合当前输出"）是同一个问题，现在有了量化证据。

## 2. 分层实验集

产物：`tmp/refactor_prep/layered_eval_summary.json`，以及四个分层明细文件 `layered_*.json`。

把 09-01 旧系统最终输出与五卷基线逐条交叉：

| | 基线正确 | 基线错误 | 合计 |
| --- | ---: | ---: | ---: |
| **旧系统正确** | 5958 | **644** | 6602 |
| **旧系统错误** | **226** | **181** | 407 |
| 合计 | 6184 | 825 | 7009 |

### 2.1 旧系统的真实价值是 644 条

旧系统相对基线净胜 **644 − 226 = 418 条**，正好等于 94.19% 与 88.23% 之间 5.96pp 的差值（0.0596 × 7009 ≈ 418）。数学自洽。

这意味着：**那套 17000 行代码、三个月、上百次全卷重跑，在基线上净赚 418 条。** 而基线用一次调用就在 226 条上反超了它。

### 2.2 保护样本（644 条）的构成

| 类别 | 条数 | 占比 |
| --- | ---: | ---: |
| 实名与实名互换 | 307 | 47.7% |
| 非人物发声误判为人物 | 213 | 33.1% |
| 实名降级为泛称 | 100 | 15.5% |
| 泛称误判为实名 | 20 | 3.1% |
| 泛称与泛称不一致 | 4 | 0.6% |

清单见 `tmp/refactor_prep/protect_set.md`。**这 644 条是所有新方案的回归线**：任何新方案在这 644 条上丢掉的，都必须用别处的收益补回来。

注意其中 213 条属于「非人物发声」——按第 1 节的结论，这一块用任务分解大概率能收回，属于"旧系统靠规则压住、新方案可以靠分解解决"的部分。

### 2.3 两边都错的 181 条才是真难点

| 类别 | 条数 |
| --- | ---: |
| 实名与实名互换 | 64 |
| 泛称与泛称不一致 | 62 |
| 非人物发声误判为人物 | 33 |
| 泛称误判为实名 | 15 |
| 实名降级为泛称 | 7 |

分卷看：

| 卷 | 两边都对 | 旧对基错 | 旧错基对 | 两边都错 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 1258 | 122 | 26 | 19 |
| 2 | 1202 | 111 | 26 | 19 |
| 3 | 1079 | 84 | 34 | 18 |
| 4 | 1277 | 152 | 61 | 71 |
| 5 | 1142 | 175 | 81 | 61 |

**去掉口径问题和任务分解能解决的部分之后，真正需要"更强的推理"才能攻克的，是 181 条，占 2.58%。** 第 4、5 卷各占 71 / 61 条。

### 2.4 目标重新分解

要每卷达到 98%（合计最多错 138 条），在 825 条基线错误中需要净修复 687 条。可分四块：

| 来源 | 条数 | 处理方式 |
| --- | ---: | --- |
| 任务分解可回收（非人物发声类） | ~213 | 已验证可解，需固化规范 |
| 泛称归并与标签一致性 | ~120 | 需要全卷实体账本 |
| 实名互换（保护样本部分） | ~307 | 需要原文反证复核 |
| 真难点 | ~181 | 需要更强的证据推理 |

这比"407 条错误、尚需净修复 269 条"这个笼统数字有可操作性得多。

## 3. 外部工具与同领域项目调研

### 3.1 结论先行

1. **执行层：不需要新工具，现有 OpenCode 已经是合适的载体**，而且已经装好、已经配好本地网关。
2. **编排层：这一轮不建议引入任何 Agent 框架。** 多篇 2026 年的选型资料给出的判断与本项目的教训一致——"如果输入、步骤和输出都固定，模型不需要自己选工具，那么几个函数加一次结构化模型调用就够了"。
3. **真正值得看的是同领域的 BookNLP 与 PDNC**：它们用另外一套方法（专门训练的模型 + 标注规范 + B3 指标）做同一件事，可以用来校准"98% 到底处于什么水平"。
4. **Codex CLI 有硬伤**，可直接排除。

### 3.2 命令行 Agent 工具对比

标注"未确认"的项表示本轮未取得可靠来源，不应直接采信。

| 工具 | 许可 | 自定义 baseURL | headless | 结构化输出 | 断点恢复 | Windows | 判断 |

| **OpenCode** | 未确认 | ✅ `provider.options.baseURL` | ✅ `opencode run` | ✅ `--format json` 事件流 | ✅ `--continue` / `--session` / `--fork` | ✅ 原生（本机已在用） | **首选，零迁移成本** |
| **CodeWhale** | MIT | ✅ 25+ provider，本地 vLLM/Ollama 一等公民 | ✅ `codewhale exec` / `serve --http` | 未确认 | ✅ 会话保存恢复 + `/restore` 回滚 | ✅ 原生 | **强候选，值得实测** |
| Codex CLI | 未确认 | ✅ `model_providers.*.base_url` | ✅ `codex exec` | 未确认 | ✅ session | ⚠️ **需 WSL2** | 硬伤：`wire_api` 仅支持 `responses`，且非 Windows 原生 |
| Claude Code | 专有 | ⚠️ 需反向代理 | ✅ `-p` | ✅ | ✅ | ✅ | 供应商锁定，与本项目"模型可替换"诉求冲突 |

| Goose / OpenHands / Cline / Continue | 未确认 | 部分 | 部分 | 未确认 | 部分 | 部分 | 本轮未逐一核实，优先级低于上面两个 |

**OpenCode 的关键优势**：本机 `~/.config/opencode/opencode.jsonc` 里已经配好了指向本地模型网关的 provider，可以不经任何改造就把 `deepseek-v4-flash` 当成执行器调用；`opencode run --format json` 输出的 JSONL 事件流里带 `tokens` / `cost` / `error` 字段，正好补上本项目手工记账的那部分。

### 3.3 编排框架对比

| 框架 | 许可 | 结构化输出 | 状态/断点 | 定位 | 判断 |
| --- | --- | :---: | :---: | --- | --- |
| **PydanticAI** | MIT | ★★★★★ | 中（消息历史 + 可接 Temporal/DBOS/Prefect） | 类型化 Agent 层 | **唯一值得局部引入的**：可替换手写 JSON 解析与修复循环 |
| LangGraph | MIT | ★★★ | ★★★★★（Checkpointer / Store / Interrupt / 时间旅行） | 状态图运行时 | 能力过剩：本项目不需要分支、人工介入、时间旅行 |
| CrewAI | MIT | ★★★★ | 中 | 角色/任务/流程 | 官方自己建议"先用 Flow 管状态，别先堆 Crew" |
| AutoGen | MIT | ★★★ | 低 | 对话式多 Agent | **微软已标记维护模式**，新项目官方建议转向 Microsoft Agent Framework |
| Google ADK | Apache-2.0 | — | 高 | Gemini/Google Cloud 生态 | 与本项目无关 |
| smolagents | Apache-2.0 | — | — | 轻量实验 | 定位是实验 |

有几个来自选型资料的判断值得直接抄下来，因为和本项目的实测教训完全一致：

- "多个 Agent 来回发言，Token 一直增加，结果未必比一个函数加一次模型调用更稳。"
- "先问一个很不酷的问题：这件事能不能用普通代码和一次模型调用做完？"
- "Agent 系统也有单向门。如果不在早期设计好 run ID、step ID、tool call ID 这些身份标识，后面要付出利息。"

**本项目正好踩在上面三条上**：堆了多个 Agent 相互发言、把能用一次调用做完的事拆成十几层、长期没有把 run ID / 产物身份固定下来（复盘中"提交时间不等于实验切换时间"就是这个问题的表现）。

### 3.4 同领域项目：这里才是真正该对照的东西

搜索发现这个任务在英文世界有正式的研究传统，而且**有专门训练的模型和公开数据集**。

**① BookNLP / BookNLP-plus**（`github.com/ppirli/booknlp`）

面向小说的完整 NLP 流水线：实体识别、**引语说话人归因（quotation attribution）**、角色名聚类（`Tom / Tom Sawyer / Mr. Sawyer / Thomas Sawyer → TOM_SAWYER`）、共指消解、事件标注。官方指标：

| 任务 | small 模型 | big 模型 |
| --- | ---: | ---: |
| 实体标注 F1 | 88.2 | 90.0 |
| 共指消解 Avg F1 | 76.4 | 79.0 |
| **说话人归因 B3** | **86.4** | **89.9** |

速度：一本 99K token 的书，10 核服务器 2.4–5.2 分钟；GPU 约 2.2 分钟。

**这是本项目最重要的外部校准点**：一个专门为这个任务训练的模型，在英文小说上说话人归因也只有 **86.4–89.9（B3）**（注意 B3 与本项目的语义口径不可直接换算，但量级可比）。本项目基线单次调用已经 88.23%（语义口径），旧系统 94.19%。

**含义：98% 这个目标，超出了公开专用系统的水平**。这不代表做不到——本项目的评分口径更宽松，且中文文本与英文的处理难度不同——但它提示：把 98% 当作硬门槛之前，值得先想清楚它对应英文世界什么水平。

**② PDNC — Project Dialogism Novel Corpus**（LREC 2022）

22 本小说的标注语料，每处引语标注：说话人、**受话人**、指称表达、引语类型（implicit / anaphoric / explicit）、以及指称映射表。**并且公开了完整的标注规范文档。**

它的"引语类型"概念正好对应本项目的「非人物发声」——说明"引号是否代表真实发言"是一个需要**正式规范**才能一致的类别，而不是靠模型直觉。第 1 节发现的 67/14 分歧，在这个框架下就是一个规范缺失问题。

建议：**把 PDNC 的标注规范文档当作制定本项目争议清单的参照**，并用 B3 这类标准指标报告结果，便于与外部对照。

**③ Grimbert**（CompNet）

小说说话人归因模型，基于 SpanBERT，前身是 `bert-quote-attribution`。提供可直接加载的预训练权重。同样以英文为主，不能直接用于中文，但**代码结构与任务定义可参考**。

**④ Audiobook Creator**（GPL-3.0）

用 LLM + OpenAI 兼容 API 把电子书转成多角色有声书。它的流程是**两步**：

1. 先用 LLM 识别出全书所有角色及其元数据（姓名、年龄、性别）
2. 再用这份角色表去给每一行文本归因说话人

**这正是本项目实验所指向的做法**：先建立稳定的实体账本，再做逐条归因。与本项目"同一角色标签不一致、泛称碎片化"的错误结构吻合。

注意许可为 **GPL-3.0**，若参考其代码需注意传染性；其**设计思路**可以自由借鉴。

## 4. 修正后的路线建议

综合两轮准备，建议下一阶段的顺序调整为：

1. **先固化评测口径**，再谈准确率。至少要明确：内心独白归人物还是归非人物、短引语如何判、泛称同义如何认定。产出应是**一份争议清单 + 冻结的评分器**，而不是继续追加规则。第 1 节已给出 81 条候选争议样本。
2. **用分层实验集驱动开发**：644 条保护样本必须先跑通，181 条真难点单独跟踪。`tmp/refactor_prep/layered_*.json` 可以直接当回归测试用。
3. **执行层继续用 OpenCode 承载**，不要新引入 CLI 工具；把 `opencode run --format json` 的事件流接进来替代手写的调用记账。
4. **只在结构化输出上引入 PydanticAI**（如果确实要引入），替换手写 JSON 解析与修复循环。**不引入 LangGraph / CrewAI / AutoGen**。
5. **按 Audiobook Creator 的两步结构重建主流程**：先出全卷角色账本（含别名归并），再逐条归因。这直接对应错误结构中最重的一块。
6. **把实名互换（307 + 64 = 371 条）单独作为一个研究问题**，用"只查原文反证"的复核机制处理，而不是重跑全部标签。
7. 报告口径对齐 BookNLP / PDNC，便于说明项目处在什么水平。
