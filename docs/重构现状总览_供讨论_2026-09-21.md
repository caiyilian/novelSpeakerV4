# 重构现状总览（供讨论）

记录日期：2026-09-21。本文完整记录：弃用旧系统后，新系统的**每个版本做了什么、成绩、难点**，以及**当前问题**和**用户约束**。供团队讨论用，可独立阅读。

---

## 一、背景与目标

**旧系统**：`src/run_label.py`（5885 行，另有 17000+ 行历史脚本），用 SenseNova Lite Flash（256K 上下文、弱模型）+ 极其复杂的机械（逐条精读 + 工具检索 + 25 轮短记忆 + 角色状态 + 证据库 + 场景审阅 + 镜像陪审）。十几天跑完五卷，最终 **94.19%**。用户因其"慢 + 臃肿 + 打补丁式演进"而弃用。

**目标**：重建一个**快、干净、可维护**的标注系统，只用一个模型，准确率尽量高。

### 旧系统最后几个版本各自做了什么（含"为什么净负"）

1. **7 月 16 日「质量模式」**：Labeler 首遍后，用 5 个"局部判断"（同一模型、相近提示、相同原文）再投一次票，终审看票数。实测 5 个同源判断错误高度相关，强局部多数能覆盖正确基线 → **净改坏 46 条**。教训：同源投票不等于独立信号。

2. **7 月 26 日「整段场景」**：场景 Mapper（把场景收紧到最多 6 句）+ 目标 Investigator + 无票 Judge + 候选 A/B 简报 + 镜像边界裁判 + 反事实复核 + 身份搜索。理论上是"多种证据链"，实际场景层**修复 190、改坏 364，净 −174**。教训：审阅器信息比能主动查原文的 Labeler 还少，却拥有改写权。

3. **8 月 3 日「引语作用域」**：止损版本——6987/7009 条直接保留基线，只改写极少数。成绩回升到 92.21%，但代价是大量调用几乎不再改变有用决策（正确样本平均 16.47 次调用）。

4. **8 月 15 日「全卷第二遍」**：首遍结束后整卷复审，166 次改写，修复 76 / 回归 64，**净增仅 12 条**。

5. **9 月 1 日「原生 256K」**（最后完整版）：放开全局 40K 限制、深查预算 20 万、工具轮数增加、9 路 scene-review + 3 路 local-entity-graph + 镜像陪审（每个入围候选最多 4 类职责 × 2 种顺序）。首遍 93.42%，复审净增 54，最终 **94.19%**。但仍有 407 条错，第 4 卷 D201–D300 仅 65%、第 5 卷 D201–D300 和 D801–D900 仅 67%。

### 旧系统为什么十几天才标注完一卷

**核心：每条对话要走一条极长的执行链，链上每一层都要多次调用同一模型。**

当前默认质量路径（逻辑任务数，非物理请求数）：

```text
小说/引号实例索引
  → 逐句 Labeler + 原文工具 + 短记忆/证据库
  → 场景 Mapper + 目标调查 + 反证/边界仲裁 + 保护门
  → 身份搜索与标签规范化
  → 首遍逐条提交
  → 全卷 scene-review：每个场景块 9 个审阅任务
  → local-entity-graph：每个场景块 3 个实体图任务
  → 候选晋级与聚合
  → 镜像陪审：每个入围候选最多 4 类职责 × 2 种顺序
  → 多种转换门槛与最终发布
```

量化的慢，来自几个叠加因素：

1. **每条约 15–18 次模型调用**：7 月 16 日一轮（还不是最终版）就记录到 **4.72 亿 annotation tokens、102955 次模型调用、并行墙钟约 98 小时**，平均每条约 14.69 次调用。
2. **同一条对话在多个层级重复求解**：同一个说话人问题，Labeler 判一次、场景层判、实体图层判、陪审再判，失败恢复还分布在每层。
3. **模型服务波动 + 大量重试**：9 月 1 日第 4 卷首遍临时日志有 1193 次模型错误、444 次全部失败事件、3984 次结构/工具结果拒绝，都要重试。
4. **TPM/RPM 限流等待 + 网络重试 + 格式化修复 + 嵌套重试 + 状态写入**。
5. **源码规模印证**：`src/*.py` 从 API 接入初期的 3597 行，增长到当前 16901 行（`run_label.py` 5885 行 + `scene_quality.py` 2970 行 + `volume_review.py` 3310 行 = 12165 行，另 GUI 1825 行）。

**关键判断**（复盘文档结论）：收益与复杂度不成正比——每加一层审阅，多次实测净改坏；底层同一模型即使换接入身份也不是多个独立模型。十几天不是单点慢，而是"每条 15–18 次调用 × 5 层重复求解 × 大量重试"的乘法效应。

## 二、用户约束（最终明确版）

1. **模型**：只用 `deepseek-v4-flash`。`deepseek-v4-pro` / `glm-5.2` / `kimi-k3` 只能当"和我讨论"的开发者角色，**绝对不能进项目当运行时组件**。
2. **时间**：**每一卷不超过 12 小时**（不是五卷总共；几分钟或几小时都行）。
3. **Token**：随便消耗，不限，不用担心。
4. **不泄露答案**：标注流程里，任何一步都不能把参考答案喂给模型。
5. **准确率**：不要求 98%，**至少 95%**。
6. **方法**：可以用多 agent、可以复用/改造市面 agent 工具（CowAgent、Codex、OpenCode 等），上下文压缩要借鉴现有工具的做法，**不要自己造轮子**。
7. 上下文占用用 **API 返回的 `usage.prompt_tokens`** 计（不要自己算 token、不要数字符）。

## 三、新系统版本演进（按时间顺序）

### 版本 1：单次基线（`baseline_annotate.py`）
- **做法**：整卷一次读进 1M 上下文，直接输出 `编号|说话人`。
- **成绩**：**88.23%**（v1 90.9 / v2 90.1 / v3 91.6 / v4 85.7 / v5 83.8）。1 次调用/卷，~60 秒。
- **难点**：泛称碎片、实名互换、无人称引语欠检测（模型几乎从不输出"非人"标签）。

### 版本 2：强制引用证据（`evidence_annotate.py`）
- **做法**：输出改成 `编号|说话人|证据行号|依据`，要求"先找证据行再写答案"。
- **成绩**：**90.74%**（+2.51pp）。1 次调用/卷，~120 秒。
- **关键发现**：这是**唯一几乎不破坏正确项**的机制（"两边都对"的 5958 条上回归率 99.21%，v1 实名互换 83→30）。消融证实增益来自"引用"本身。

### 版本 3：两步法 / 角色账本（`twopass_annotate.py`）
- **做法**：先让模型产出全卷角色账本（canonical + 别名），再逐条归因。
- **成绩**：88.63%（混合，不稳定）。
- **难点**：账本解决"实名降级为泛称"（v5 48→3），但收益被其他波动抵消；逐卷方向不一致。

### 版本 4：整卷 + 账本（`evidence_annotate.py --with-ledger`）
- **做法**：强制引用证据 + 注入角色账本。
- **成绩**：**91.47%**（v1 95.1 / v2 91.2 / v3 94.7 / v4 89.0 / v5 88.3）。2 次调用/卷，~3 分钟。

### 版本 5：身份消解（`identity_resolve.py`）
- **做法**：把标注系统**实际输出的词表**交给模型做专注归并（叶克柏→叶克伯等错字/别名），再归一。
- **成绩**：91.65%（+0.19pp，主要 v2 +1.19）。
- **来源**：借鉴 CowAgent 的"Deep Dream 蒸馏"思想（专注小任务比整卷对别名敏感）。

### 版本 6：三阶段流水线（`pipeline_v1.py`）—— 失败
- **做法**：A 引号用途判定 → B 角色账本 → C 受限归因。
- **成绩**：负（三卷变差，v3 掉 6pp）。
- **教训**：独立 A/B 分类召回 91% 但精确率 49%，串进流水线过判，误差不可逆传导。

### 版本 7：分块多轮（`chunked_multi_turn.py`）—— 失败
- **做法**：每 60 条重置对话 + 6 条锚点 + 动态蒸馏账本。
- **成绩**：负（v1 89.25% < 整卷 94.96%）。
- **教训**：每 60 条粗暴丢弃上下文，丢失跨块信息；且解析 fallback 把模型回显的"D编号"当成了说话人。

### 版本 8：连续多轮 Agent（`cont_agent.py`）—— 当前最优
- **做法**：
  - **持续单对话**，按编号逐条标注，追踪"谁上一句说"（修实名互换）；
  - **角色账本**预载（canonical+别名），边标边累积；
  - **token 阈值压缩**：`usage.prompt_tokens` 超 60 万（1M 窗口 60% 安全余量）时，把历史蒸馏成账本+最近锚点（借鉴 Codex 本地压缩：保留 user 消息 + 蒸馏 assistant 回复成 handoff summary）；
  - **checkpoint** 每 50 条落盘 + `--resume` 断点续跑。
- **成绩**：**92.31%**（v1 93.5 / v2 88.6 / v3 94.7 / **v4 92.4 / v5 92.7**）。五卷并行 ~4 小时，单卷 ~3.5 小时。

### 版本 9：+ 保守泛称归一 + 空标签兜底
- **做法**：对 cont 结果做"只归并泛称↔泛称"的账本归一 + 空标签用 evledger 填补。
- **成绩**：**92.77%**（+0.46pp，主要 v2 +2.3）。

## 五、关键发现与坑（每个都花了代价换来）

### 5.1 「无人称引语」是双刃剑（最重要洞察）
- 整卷一次读：**欠检测**（把风声/拟声/被引用的说法错标成人）。
- 多轮 Agent：**过检测**（把人的话错标成非人）。
- 在非人物多的卷（v4/v5）→ 多轮过检测正好修正整卷欠检测 → **赚**；在非人物少的卷（v1/v2）→ 多轮过检测误伤真对话 → **亏**。净 +0.84pp。

### 5.2 两个解析 bug（都导致结果污染后才发现）
1. **D编号 bug**：模型把回显的"D0002"当说话人，解析 fallback 接受了它。
2. **"说话人"污染**：模型在重试时字面输出"说话人"三个字被当成标签（v2/v3/v4 各污染 422–646 条）。
- **通用教训**：解析模型输出时，fallback 绝不能接受"任意短字符串"，必须黑名单提示词/编号/标点；长多轮对话会格式漂移，每条 user 消息都要重复格式约束。

### 5.3 token 计数坑
- 上下文大小 = **最后一次 call 的 `prompt_tokens`（覆盖）**，不是累加（累加会因 prompt 含全部历史而虚高）。

### 5.4 机械规则是死路（4 条量化证据）
| 规则 | 结果 |
| --- | --- |
| "名字+说"显式归因 | 冲突项里 84% 是规则错绑 |
| 可疑集合（±2 行 ≥2 具名角色） | 覆盖 77%，零区分度 |
| 元语言标记（一副…模样/也就是…） | precision 21.8% |
| 引用真实性校验 | precision 8.1% |

### 5.5 投票/温度采样无效
- 同模型多 prompt 投票 ≈0、温度 0.7 采样两次塌到 50%——同模型错误高度相关，无独立信号。

### 5.6 「逐条」vs「整卷」的权衡
- 逐条多轮在实名互换段有局部优势（D375–394 100% vs 整卷 80%），但全卷上"逐条局部视角"在开头/场景切换处丢失全局身份、误判无人称引语。
- 结论：**两者互补**，多轮 Agent 整体略优（92.31% vs 91.47%），主要靠难卷的大幅提升。

## 六、当前剩余问题：203 条共同盲区

对 7009 条逐一对比（连续多轮 vs 整卷）：

| 情形 | 条数 |
| --- | ---: |
| 两方案都对 | 6075 |
| 多轮独对 | 395 |
| 整卷独对 | 336 |
| **两方案都错** | **203** |

**这 203 条是连续多轮 + 整卷 + 旧系统 三方案共同盲区**（旧系统在这 203 条上对了 **0 条**）。

构成：
| 类型 | 条数 | 性质 |
| --- | ---: | --- |
| named→named（实名互换，三方案都错） | 101 | 真·语义难点 |
| generic→generic（泛称口径，商行手下 vs 米隆商行的人） | 36 | 部分可归一救回 |
| named↔generic（身份判定错） | 54 | 真·语义难点 |
| nonperson→named（真·无人称引语欠检测） | 9 | 少 |
| 空标签 | 3 | 可兜底 |

进一步看：**72%（146 条）是"答案单候选"**（标注者明确给唯一答案，三模型都错，是真难点）；28%（57 条）是复合标签（口径相对宽松）。

### 当前结论
- 92.77% 是 `deepseek-v4-flash` 干净方法（多轮 Agent + 泛称归一）的**当前极限**。
- 离目标 95% 差 2.23pp，离旧系统 94.19% 差 1.42pp。
- 剩余 203 条盲区主要是**真·语义难点**（连旧系统的弱模型+17000 行+十几天都 0 对），少量是答案口径争议。

## 八、平台层坑（后续任何批量任务可复用）

1. **批量任务必须显式 `reasoning_effort:"none"`**：v4-pro / glm-5.2 默认思考会烧光输出预算；deepseek-v4-flash 整卷批量开推理 390s 只完成 152/1459。
2. `kimi-k3` 只接受 `model`+`messages`（传 `temperature`/`max_tokens` 会 HTTP 400）。
3. `response_format: json_schema` 不支持。
4. 1M 上下文真实可用（整卷约 9.5 万 token）。
5. 本地模型池 `127.0.0.1:18787`：20 个账号，各有 rate_limit，**五卷并行会触发 cooldown**，实测降到 ~2.3 条/分钟/卷；单卷跑能到 ~13 条/分钟。
