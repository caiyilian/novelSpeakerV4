## 一、为什么"瓶颈在编排"成立

先对齐事实：旧系统用 SenseNova Flash Lite（256K、远弱于 deepseek-v4-flash）做到五卷 94.19%，当前 v4-flash 干净方法 92.77%。单卷耗时 ~3.5 小时，离 12 小时预算上限还有 3 倍以上的余量。**时间和 token 都还没花到上限，确实不能说到了瓶颈。**

更关键的是，把当前最优方案 `cont_agent.py`（311 行）与主流 agent harness 逐项对照，编排上的欠账非常具体：

| 编排维度 | 当前 cont_agent 的做法 | 主流工具的成熟做法 | 差距 |
| --- | --- | --- | --- |
| 并行 | **完全串行**，逐条标注，五卷各跑一个进程 | 子代理 fan-out/fan-in，父代理只收蒸馏结果 | 墙钟时间被串行锁死，12h 预算只用了 30% |
| 任务分解 | 一个 agent 包打天下（标注+身份追踪+非人判断+证据） | 专项小任务拆分（已实测：无人称引语拆出后召回 0%→91%） | 已验证有效的分解只停留在探针，没进主流程 |
| 上下文压缩 | 60 万 token 阈值后**整段丢弃式蒸馏**成账本+锚点 | 先机械 prune 再 LLM 摘要、保留尾部精确轮次、结构化模板、压缩后重放最近指令 | 压缩是信息损失最大的一环，用的是最粗的做法 |
| 工具调用 | 只有 1 个 `read_novel_lines`；输出靠**自由文本解析 + fallback** | 结构化提交工具（tool call schema 即输出契约）、只读检索工具组 | 两个污染 bug（D编号、"说话人"）都来自自由文本解析 |
| 记忆层 | 账本只在开头预载 + 压缩时一次性重写，无增量维护循环 | mem0 式 ADD/UPDATE/DELETE/NONE 增量操作 + 证据锚定 + 冲突更新 | 账本在长跑中会漂移，没有冲突解决机制 |
| 状态持久化 | 每 50 条手写 checkpoint JSON | append-only 事件日志 + 投影派生上下文（deepseek-harness），fork/resume/replay 统一 | 恢复逻辑与上下文构造耦合，无法回放审计 |
| 分歧处理 | 无（单一路径输出即终局） | 对抗验证（skeptic subagent 专门反驳）、judge panel | 与整卷方案互补的 731 条分歧被白白浪费 |

**结论：用户的判断有源码级证据支持。** 当前方案在七个编排维度上都只用了最原始的形态，而每一维都有经过大规模生产验证的现成做法可以移植。旧系统证明了"编排可以补偿模型"，但它的实现方式（17000 行、每条 15-18 次调用、五层重复求解）是错的；正确的问题是：**能否用主流工具验证过的编排模式，在 v4-flash 上以 1/10 的代码量拿到那 1.42pp 甚至更多**。

### 2.2 opencode：压缩的正确姿势与子代理模型（最重要借鉴源）

**压缩两阶段**（`packages/opencode/src/session/compaction.ts`）：

1. **先 prune 后摘要**。倒序遍历消息，跳过最近 2 个 user 轮次，保护最近 `PRUNE_PROTECT = 40_000` token 的工具输出；更老的工具输出标记 `compacted` 并以占位符 `[Old tool result content cleared]` 替代；只有可回收量超过 `PRUNE_MINIMUM = 20_000` token 才执行。**能不花模型调用就不花。**
2. **尾部选择精确到轮次边界**：`select()` 按预算（可用窗口的 25%，clamp 在 2K–15K token）从后往前整轮保留，预算不足一整轮时 `splitTurn()` 在轮内找可切割点。摘要只覆盖 head，尾部原文精确保留。
3. **结构化摘要模板 + 增量更新**（`packages/core/src/session/compaction.ts`）：固定 `## Objective / ## Important Details / ## Work State(Completed/Active/Blocked) / ## Next Move / ## Relevant Files` 模板；二次压缩时把 `<prior-summary>` 与新对话一起给模型，明确"冲突时新对话赢、丢弃即丢失"。
4. **压缩后重放**：自动压缩完成后，把最后一条真实 user 消息重放给模型，或注入合成的 "Continue if you have next steps" —— 模型从最近指令继续，而不是从摘要里迷失。
5. **专门的隐藏 compaction agent**：禁全部工具、可绑定不同模型，压缩本身是系统任务而非主对话的一部分。

**子代理模型**（`tool/task.ts` + `agent/agent.ts`）：Agent 是**纯配置**（prompt/权限/模型绑定），执行循环共享；子代理通过 task 工具派生独立 session，父代理只收到最终报告。`explore`（只读）、`general`（通用）、`compaction`（隐藏）即内置分工。

> 对本项目的价值：cont_agent 的"阈值蒸馏"是这套机制的粗糙原型——没有 prune、没有尾部精确保留、没有增量摘要、没有压缩后重放。直接照抄这套流程即可把压缩质量提到生产水位。

### 2.3 Codex CLI：handoff 摘要与用户消息保护

`codex-rs/core/src/compact.rs` + `prompts/templates/compact/prompt.md`：

1. **压缩提示词定位为"工作交接"**："Create a handoff summary for another LLM that will resume the task"，四要素=进展与关键决策、约束与偏好、剩余步骤、关键数据。摘要为**续跑**而写，不为存档而写。
2. **用户消息逐字保留**：重建历史 = `[近期用户消息原文（倒序填满 20K token 预算，COMPACT_USER_MESSAGE_MAX_TOKENS）] + [摘要]`。assistant 回复与工具结果全部物理删除。用户的指令是最不该被改写的信息。
3. **初始上下文重注入的位置语义**：`InitialContextInjection` 区分 pre-turn 与 mid-turn——mid-turn 压缩必须把初始上下文插在**最后一条真实 user 消息上方**，因为模型被训练为期望压缩摘要是历史最后一项。这种协议级细节不读源码根本想不到。
4. **编号自动压缩窗口**（`auto_compact_window.rs`）：每次压缩是一个带序号的 window，resume 时恢复窗口状态，压缩边界可持久化校验（源与保留轮次不重叠、占用不增长）。
5. **压缩超限时的降级**：压缩请求本身超窗时，从历史开头逐项删除（保前缀缓存），而不是直接报错。
6. **官方警告原话**："Long threads and multiple compactions can cause the model to be less accurate. Start a new thread when possible to keep threads small and targeted." —— **长会话+多次压缩会降精度，能开新会话就开新会话**。这条直接支持本文架构选择"分块短会话"优于"单长会话+反复压缩"。

### 2.4 deepseek-harness（dsh）：事件日志即事实源

DeepSeek 官方 agent harness（MIT，2026-08 开发者预览，GitHub 趋势第一）。其 session 设计（`packages/core/session/src/index.ts`）是最值得移植的架构思想：

1. **append-only 事件日志是唯一事实源**：所有 user/assistant/tool 事件顺序 append，带 `seq`，深冻结，不可变。
2. **模型可见上下文是日志的投影**：`deriveMessages()` 沿 surface 节点序列派生 LLM 历史；压缩是一个 `replace` surfaceOp——**从投影中删除被遮蔽节点，但原始日志完整保留**。审计、回放、fork、resume、token 统计全部从这同一条日志派生。
3. **增量缓存**：投影按尾部增量 O(新节点) 扩展，surface 变更才重建。
4. **fork 语义**：可在任意 turn 边界 fork 会话（`parentSession, seedLength`），天然支持"同一前缀、不同分支"的对照实验。
5. 一切皆插件（Cordis）+ PTC（程序化工具调用：模型输出 TS 代码编排多次工具调用一次执行，减少 LLM 往返）+ waterfall 事件（插件链可拦截/改写模型请求与工具执行）。

> 对本项目的价值：现在 `results{} + ledger + recent + cursor` 的手写 checkpoint 应该改成**事件日志**——每条标注决策、每次工具调用、每次账本变更都是一条 append 事件；模型上下文、断点恢复、准确率评分、成本审计都是这条日志的不同投影。这也是复盘文档第 9.4 节"统一 run ID / 产物身份"的落地方式。PTC 思想对应本项目：标注 agent 一轮可以输出"读取 100-160 行 → 读取 4020-4050 行 → 提交 5 条标签"的编排代码，一次执行，省两轮 LLM 往返。

### 2.5 mem0：记忆操作语义（账本维护循环的模板）

`mem0/configs/prompts.py` 提供了生产级记忆提示词全套：

1. **记忆操作四选一**：`ADD / UPDATE / DELETE / NONE`，UPDATE 保持原 ID 且必须附 `old_memory` 字段（可审计 diff）。
2. **V3 增量抽取**（ADD-only + linking）：新记忆带 `linked_memory_ids` 挂到已有记忆上，形成记忆图；**时间锚定**（相对时间必须换算成 Observation Date 的绝对日期）；**专名保留**（"最高的价值细节，泛化成类别是致命错误"）；**自包含**（每条记忆脱离上下文可读）；**防回声**（assistant 复述 user 的内容不重复抽取）。
3. **程序性记忆**：agent 执行历史的逐步结构化摘要模板（Action/Result/Findings/Errors/CurrentContext）。

> 对本项目的价值：角色账本的维护循环应该照搬这套语义——"叶克柏→叶克伯"就是一次 UPDATE（保留 old_memory 可审计），新登场角色是 ADD，身份揭示（"女孩"=赫萝）是带 linked_memory_ids 的关联。**每条账本变更必须附原文行号证据**，这既符合 mem0 的 evidence-bound 原则，也吻合本项目"强制引用证据是唯一不破坏正确项的机制"的实测结论。letta-code 则补充了存储形态：记忆即文件系统（每目录一个 MEMORY.md 索引，git 备份），agent 用文件工具自行维护——本项目的账本同样应该是一个 JSON 文件 + 投影渲染，而不是埋在对话历史里。

### 2.6 aider：repo map → "novel map" 的直接类比

`aider/repomap.py`：tree-sitter 提取每个文件的 def/ref 标签 → 标识符共现建图 → PageRank 排序（聊天中文件 ×50、被提及标识符 ×10、长命名 ×10、私有/重载 ×0.1、引用频次开平方压高频）→ 二分搜索渲染进 token 预算（默认 ~1024 token）。

> 对本项目的价值：这就是"novel map"的实现模板。**角色×场景共现图**：节点=角色（账本实体），边=同场景共现/对话交互，权重=共现频次；每个角色的"def"=首次命名行，"ref"=所有出现行。当标注 agent 处理某块时，不需要全量账本，只需要 PageRank 出的"与本块相关的 top-K 角色卡片"——账本投影按块定制，token 预算固定。这直接解决"账本越长越稀释注意力"的问题。

### 2.7 pi-mono：极简哲学与会话树

`packages/agent/src/harness/compaction/compaction.ts`：

1. 摘要模板与 opencode 同构（Goal/Constraints/Progress(Done/InProgress/Blocked)/KeyDecisions/NextSteps/CriticalContext），且**增量更新提示词**明确规则：PRESERVE 旧摘要全部信息、Done 项迁移、冲突项更新。
2. 分支摘要（branch-summarization）：会话是 append-only 树（JSONL），压缩/分叉都是树节点——与 dsh 事件日志同一家族的设计。
3. 全项目哲学：系统提示+工具定义 <1000 token，只有 read/write/edit/bash 四个原子工具。**"模型不需要的工具定义不要给"**——每个工具 schema 都在吃每轮上下文。

### 2.8 文献层的关键共识（用于设计决策背书）

1. **Anthropic 官方三招**：compaction（保流程连续）、结构化笔记/agentic memory（NOTES.md 式外部持久，里程碑型任务更优）、子代理（探索性工作烧子代理的上下文，只返回 1-2K token 蒸馏结论）。上下文管理实测：memory tool + context editing 组合在 agentic search 上 +39%。
2. **Claude Code 防御分层**（prune→compact→emergency truncation→overflow recovery，便宜的层先跑）：`AUTOCOMPACT_BUFFER_TOKENS=13_000`、连续压缩失败熔断 `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES=3`（曾经全局每天烧 25 万次失败调用）。压缩后必须**重建工作现场**（重注入最近读过的文件/技能/工具声明），否则是用一个病换另一个病。
3. **子代理编排的生产共识**（Wikantik/pooniya/zylos 三篇互证）：隔离先于并行（子代理核心价值是上下文隔离不是加速）；层级保持 2-3 层；fan-in 必须有聚合器；**控制流是确定性代码，只有逐条判断给模型**（可复现、可断点、可审计）；对抗验证（skeptic 专门反驳）是过滤"看似合理但错"的最有效手段；并行上限 ~8 个子代理，超过则合成质量崩。
4. **durable execution 阶梯**（matthewswong）：最低一级"幂等键 + steps 表"就够三步流水线用——本项目现有 checkpoint 已在该层级，dsh 事件日志是同级更干净的实现；**不需要 Temporal/Restate 这类工作流引擎**。
5. **LLMLingua-2 的教训**：通用提示压缩器在长文档检索上有增益，但在代码/数学/结构化 schema 上退化，且跨语言（中英混杂）场景会损坏语义脚手架（实测 gemini-lite 上 -60pp）。**对本项目：不引入 LLMLingua 类通用压缩器，压缩必须走"账本蒸馏 + 模板摘要"的领域语义路线。**

## 三、新系统设计

### 3.0 设计原则（从调研和历史教训提炼）

1. **控制流是代码，判断才是模型**（Wikantik 共识 + 复盘"没有持续用消融淘汰无效层"的教训）。fan-out、重试、聚合、发布全部是确定性 Python；模型只做逐块判断。
2. **子代理要短，不要长**（Codex 官方警告 + 分块多轮失败教训的正面利用：上次失败是因为"每 60 条粗暴丢弃上下文"，不是因为分块本身——这次每块是**自足的自然场景**，跨块状态走账本文件，不走对话历史）。
3. **同源多数不算证据，原文反证才算**（7·16 同源投票净 -46、镜像陪审门禁挡住 133 条正确候选的教训）。裁决层不许投票，只允许"附行号证据的反驳"。
4. **答案隔离在环境层**：标注 agent 的运行目录里没有 answers.txt；评分器只在全部标注落盘后运行。
5. **每一层必须自证净收益**：接入分层实验集（644 保护样本 + 181 真难点），任何一层回归保护样本即默认关闭。

### 3.1 总架构：五阶段流水线

```text
[阶段0 确定性索引]（纯代码，无模型）
  引号实例索引（复用 quote_occurrence.py）
  场景切分（叙述段/章节边界 + 对话密度，目标每块 30-80 条引语）
  角色×场景共现图骨架（aider PageRank 模板，先按表面名）
        │
[阶段1 全卷账本]（1-2 次调用，复用 twopass）
  LedgerBuilder：整卷一次读 → 角色账本 v0（canonical+别名+首次命名行）
        │
[阶段2 分块并行标注]（fan-out，本方案核心）
  每块一个 BlockLabeler 子代理（全新上下文，多轮逐条）
  输入：账本投影（aider 式 top-K 角色卡片）+ 本块全文（自然场景+前后 margin）
  输出：submit_label 工具结构化提交（说话人|证据行号|依据）
  账本变更：mem0 式 ADD/UPDATE 提案 → 单写者序列化合并（带行号证据）
        │
[阶段3 专项任务]（并行，互不依赖）
  QuoteTyper：无人称引语独立判定（探针已验证召回 91%）
  IdentityResolver：输出词表归并（已验证 +0.19pp）
        │
[阶段4 对抗裁决]（fan-in，只处理分歧与低置信）
  候选集 = 块标注 vs 整卷基线(evidence_annotate) 分歧 ∪ QuoteTyper 冲突 ∪ 账本冲突
  每条分歧派一个 Refuter 子代理：全新上下文 + 宽原文窗口 + 两个候选
  任务不是选边，是"找出其中一个候选的行号级反证"；找不到反证 → 保留块标注
        │
[阶段5 难点深挖 + 发布]（确定性收尾）
  剩余未裁决 → reasoning_effort=high 单代理宽上下文深查（当前唯一未测杠杆）
  泛称归一 + 空标签兜底（复用版本9，+0.46pp）
  冻结评分器评分 → 分层报告（保护样本回归数必须=0）
```

### 3.2 Agent 分工表

| Agent | 模式 | 上下文规模 | 职责 | 借鉴来源 |
| --- | --- | --- | --- | --- |
| **Orchestrator** | 纯代码 | — | 索引、切分、fan-out/in、账本单写者、checkpoint、发布 | dsh 事件日志；Wikantik 确定性编排 |
| **LedgerBuilder** | 整卷单调用 ×1-2 | ~100K tok | 角色账本 v0 | 现有 twopass（91.47% 组合的一部分） |
| **BlockLabeler** ×N | 块级多轮子代理 | 每块 15-30K tok，全程 <60K | 逐条标注本块引语（多轮保话轮追踪） | opencode task 子代理；Codex"开新线程" |
| **QuoteTyper** | 整卷 1 次 + 候选复核 | ~100K tok | 独立判定"是否真实发言"（A/B + 短依据） | 重构准备二探针（召回 91%） |
| **IdentityResolver** | 1 次 | ~10K tok | 输出词表归并 | 现有 identity_resolve（+0.19pp） |
| **Refuter** ×分歧数 | 单条专项子代理 | ~20-40K tok | 对一条分歧找行号级反证，不投票 | pooniya Verifier 模式；旧系统反证思想的正确实现 |
| **DeepDiver** | 单条，reasoning=high | ~100-200K tok | 最后 ~200 条难点的宽上下文深查 | refine_divergent.py（进行中） |
| **Scorer** | 纯代码 | — | 冻结评分器 + 分层报告 | 现有 09-01 冻结评分器 |

层级恰好 2 层（Orchestrator → 各 worker），符合生产共识。

### 3.3 一次处理多少：块大小的论证

**目标区间：每块 30-80 条引语 / 原文 10-20K token，多轮标注后总上下文 <60K token。**

依据：

1. **下界**：旧系统场景收紧到 6 句导致净 -174（场景层信息不足却拥有改写权）；cont_agent 半径 8 行在场景切换处丢全局。→ 块必须覆盖完整自然场景。
2. **上界**：Codex 警告长线程+多次压缩降精度；"Lost in the Middle"实测中间段召回劣化。60K 以下处于 v4-flash 1M 窗口的高保真区（整卷 95K 已可用，块级更小更安全）。
3. **多轮收益保留**：cont_agent 的核心优势（话轮追踪修实名互换）来自同一会话内逐条推进——块内逐条多轮完整保留该优势；块间状态走账本而非对话，避免 chunked_multi_turn 的"粗暴丢弃"失败。
4. **并行度**：每卷 ~1400 条 ÷ ~50 条/块 ≈ 25-30 块。本地模型池 20 账号，实测单卷 ~13 条/分钟、五卷并行触发 cooldown 降到 ~2.3 条/分钟/卷。按块并行 6-8 路（pooniya 经验上限 8），单卷首遍估算：30 块 × 50 条 × ~5s/条 ÷ 8 路 ≈ **16-25 分钟/卷**。即使模型池限流降到 1/3 速度也不到 1.5 小时。

### 3.4 每个 agent 的多轮上下文设计

**BlockLabeler（唯一的多轮 agent）**：

```text
[system] 标注员规范（口径铁律：内心独白归人物、无人称引语四类判据、输出只走 submit_label）
[user 1] 本块角色卡片（账本投影 top-K，每张卡片：canonical+别名+首次命名行+与本块的关系）
[user 2] 前情锚点（前一块末尾 5 条已标结果：D编号+说话人，跨块话轮连续性）
[user 3..] 逐条：D编号 + 所在行 ±radius 原文（radius 默认 10，多轮中 agent 可用工具扩读）
[assistant] 每轮 1-N 个 submit_label 工具调用（结构化）
```

- **块内不压缩**：60K 上限内一次跑完，杜绝压缩损失。这是"用子代理隔离代替长会话压缩"的刻意选择（Codex 官方建议的直接应用）。
- **跨块交接走两个通道**：① 账本文件（身份状态）；② 前情锚点（话轮状态）。对话历史本身不跨块——这是与 chunked_multi_turn 失败版的本质区别（它丢了身份也丢了全局）。

**单调用 agent（LedgerBuilder/QuoteTyper/IdentityResolver/Refuter/DeepDiver）**：全部一次性宽上下文输入 + 单次（或少轮工具循环）输出，无多轮状态，无压缩需求。

**若未来确需长会话 agent**（如全卷连续性实验）：按 opencode 两阶段实现——先 prune 旧工具输出（保护最近 40K token），再按模板增量摘要，保留尾部整轮，压缩后重放最近指令；触发阈值 = `usage.prompt_tokens`（用户口径）超过窗口 75%，连续失败 3 次熔断（Claude Code 熔断参数）。

### 3.5 工具调用设计

**原则：工具少而精（pi-mono 哲学），输出即工具（schema 即契约）。**

| 工具 | 参数 | 返回 | 设计依据 |
| --- | --- | --- | --- |
| `read_novel_lines` | start, count(≤60) | 行号:原文 | 现有工具保留；返回截断保护（opencode TOOL_OUTPUT_MAX_CHARS=2000 思路） |
| `search_novel` | keyword, max_hits(≤20) | 命中行号+上下文 1 行 | 跨场景查证（"这个名字上次出现在哪"）；grep 式确定性检索，比让模型翻全文省 token |
| `get_quote_context` | d编号, radius | 指定引语的行窗 | 精确回查（quote_occurrence.py 索引复用） |
| `submit_label` | d编号, speaker, evidence_line, reason(≤40字) | 接收/拒绝+原因 | **核心改动**：结构化提交替代自由文本解析。schema 校验在 harness 侧：D编号必须在块内、evidence_line 必须在原文范围、speaker 命中黑名单（"说话人"/编号/标点）直接拒绝并要求重提——把两个历史污染 bug 消灭在协议层 |
| `propose_ledger_update` | op(ADD/UPDATE), canonical, alias, evidence_line, note | 排队确认 | mem0 操作语义；agent 提案、Orchestrator 单写者合并，避免并发写冲突 |

工具结果全部带行号、紧凑、可截断；**工具 schema 总量控制在 1K token 内**。

### 3.6 记忆层设计

**一条铁律：账本文件是唯一共享可变状态；对话历史不是记忆。**

```text
memory/
  ledger.json          # 角色账本（canonical/aliases/first_named_line/notes/历史变更append-only段）
  ledger_events.jsonl  # 账本变更事件流（ADD/UPDATE 提案+采纳/拒绝+证据行号，append-only）
  quote_types.json     # QuoteTyper 判定结果（d编号 → A/B+依据）
  run_events.jsonl     # 全量事件日志（dsh 式：每次调用/工具/提交/账本变更一条事件）
```

1. **写路径**：BlockLabeler 提案 → Orchestrator 单写者序列化合并 → 冲突时**新证据赢**（opencode 增量摘要"冲突时新对话赢"的账本版），被覆盖的旧值进 events 留痕（mem0 的 old_memory 审计字段）。
2. **读路径**：账本不整量注入。aider 式投影——按本块共现图 PageRank 出 top-K 角色卡片，K 由 token 预算控制（默认 2K token）。
3. **防污染**：账本只收"带行号证据的身份事实"；评分用的 verified identities 独立冻结，与运行时账本分开（复盘第 6.2 条防循环验证）。
4. **事件日志即 checkpoint**：`run_events.jsonl` append-only；resume=重放日志恢复 results/账本/cursor；fork=复制前缀日志开分支（对照实验用）。这把现有手写 checkpoint、dsh 的 deriveMessages、durable execution 阶梯最低级统一成一个机制。

### 3.7 上下文压缩设计（汇总决策）

| 场景 | 决策 | 来源 |
| --- | --- | --- |
| 块标注 agent（主力） | **不压缩**。块大小硬约束在 60K 以内，压缩需求被架构消除 | Codex"开新线程"警告 |
| 跨块状态 | 账本蒸馏 + 前情锚点，**对话历史不跨块** | opencode 子代理隔离；Codex handoff |
| 长会话 agent（如启用） | 两阶段：prune 旧工具输出（保护 40K）→ 模板增量摘要 + 尾部整轮保留 + 重放最近指令；阈值=prompt_tokens>75% 窗口；连续失败 3 次熔断 | opencode compaction.ts 常量；Claude Code 熔断 |
| 摘要模板 | 领域定制版 anchored summary：账本变更/已标区间/未标区间/争议清单/下一步；**禁止自由摘要** | opencode SUMMARY_TEMPLATE + Codex handoff 四要素 |
| 不采用 | LLMLingua 类通用 token 压缩器（跨语言损伤实测）、递归摘要套娃（Amp 的批评） | arXiv 2606.03618；lexifina 横评 |

### 3.8 12 小时预算校核（单卷）

| 阶段 | 调用量估算 | 时间估算（无限流/保守限流） |
| --- | --- | --- |
| 0 索引 | 0 | 秒级 |
| 1 账本 | 2 | 3-5 分钟 |
| 2 分块标注 | ~30 块 × ~55 调用 ≈ 1650 | 0.5-1.5 小时（8 路并行） |
| 3 专项 | ~10 + 候选复核 ~100 | 10-30 分钟 |
| 4 对抗裁决 | ~300 分歧 × 1-3 调用 ≈ 600 | 0.5-1.5 小时（8 路并行） |
| 5 深挖+收尾 | ~200 × 1（reasoning=high 慢）+ 归一 | 1-3 小时 |
| **合计** | **~2800 调用/卷（vs 旧系统 ~2 万次）** | **2.5-7 小时，预算内留 1 倍以上余量** |

余量是有意保留的：它是"难点深挖可以开更大半径/更多复核"的调节空间，而不是再叠一层永久审阅的理由。

### 3.9 实验路线图（先小后大，每步有退出标准）

1. **E0 基线冻结**：现有 cont 92.31% / +归一 92.77% 产物与分层实验集对齐，确认 644 保护样本在当前输出上的命中数。
2. **E1 分块并行 vs cont_agent**（单卷 v5，~50 条样本先行）：验证块化不劣于连续多轮。退出标准：样本集 ≥ cont 且保护样本零回归。
3. **E2 +QuoteTyper 合流**：预期收回无人称引语（准备二：整卷基线该类全丢 280 条中的大头）。先冻结口径：内心独白归人物（对齐答案 67/14 的多数派）。
4. **E3 +对抗裁决**：只在分歧集上运行，报告修复/回归/弃权三数，弃权率 >30% 说明 Refuter 设计失败。
5. **E4 +DeepDiver**：最后手段，只打 E3 后的残余。reasoning=high 的成本单独报告。
6. **E5 五卷全量**：只在 E1-E4 全部通过退出标准后跑。验收 ≥95%（用户新目标），同时报每卷严格/语义双口径与最差窗口。

### 3.10 明确不做什么

- 不引入 LangGraph/CrewAI/AutoGen/Temporal（准备二结论 + durable execution 阶梯：steps 表已够）。
- 不引入 LLMLingua 类通用压缩器（跨语言损伤）。
- 不做同源多路投票/镜像陪审（三次实测净负）。
- 不写机械正则规则（四条量化失败证据）。
- 不把答案文件放进任何 agent 可见目录。
- 不用 v4-pro/glm-5.2/kimi-k3 当运行时组件（用户约束）。
- 不为"跑完"而加永久层：每一层默认关闭，凭净收益上岗。

## 五、一句话总结

旧系统证明了编排能补偿模型，但它的补偿方式是把同一问题在五层重复求解；2026 年的主流 agent 工具已经给出了每个编排维度的成熟答案——**子代理隔离代替长会话压缩（Codex/opencode）、事件日志代替手写 checkpoint（dsh）、结构化提交代替自由文本解析（opencode schema）、账本操作语义代替整段重写（mem0）、共现图投影代替全量注入（aider）、对抗反证代替同源投票（生产共识）**。本方案把这些零件组装成一条 2 层、8 路并行、单卷 2.5-7 小时的流水线，剩余预算全部留给 203 条共同盲区的深挖。是否按 E0→E1 启动，请指示。
