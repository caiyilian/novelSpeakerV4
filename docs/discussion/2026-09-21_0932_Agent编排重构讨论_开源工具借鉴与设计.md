# Agent 编排重构讨论：从 92.77% 出发的路线设计与开源工具借鉴

本文做四件事：

## 一、先回答核心判断：瓶颈到底在哪

用户判断：**旧系统（SenseNova Flash Lite 256K，模型能力远弱于 deepseek-v4-flash）能靠编排到 94.19%，当前新系统只有 92.77%，说明编排上限远没到**。这个判断在数据上站得住，有三条证据链：

**证据 1：时间预算还有 3.4 倍空间。** 当前最优方案（cont_agent）单卷约 3.5 小时，预算 12 小时。也就是说我们有 **8.5 小时/卷的"可购买信息增量"** 还没花出去。旧系统单卷两三天、每条 15–18 次调用换来了 94.19%——不是调用次数本身有价值，而是那些调用里有一部分（逐条上下文 + 原文深查 + 角色状态追踪）创造了"整卷一次读"没有的信息。我们的任务是把这部分**有信息增量的调用**识别出来、用便宜的方式重建，而不是复刻整套机械。

**证据 2：两条通道已证明"互补性"真实存在。** cont（逐条多轮）与 evledger（整卷+证据）在 7009 条上：两方案都对 6075、多轮独对 395、整卷独对 336、都错 203。**395+336=731 条分歧本身就是尚未开采的信号**——两条通道的信息来源不同（局部交替追踪 vs 全卷视野），分歧点就是"值得花推理预算的地方"。现在我们只是简单信多轮（92.31%），没有任何仲裁机制。

**证据 3：纯模型杠杆只剩一个未测。** 十条机制已被数据证伪（投票、温度采样、规则归因、独立分类层串联……），唯一没试过的是"对分歧条目开 reasoning_effort=high"（`refine_divergent.py` 正在验证）。即使它有效，也只覆盖分歧子集；编排侧（仲裁、深查、记忆、压缩）同样有明确的增量空间。

**但必须同时说清反面**：两方案都错的 203 条里，72% 是"答案单候选"的真语义难点，连旧系统 17000 行 + 十几天也是 0 对。这部分不是编排能解决的，是模型能力边界。**所以合理的目标定位是：编排侧追平并小幅超过旧系统 94.19%（预期 94.2–94.8%），95% 是否可达取决于 203 条里有多少能被"开推理 + 场景级深查 + 证据链"攻下。** 这与用户"12 小时内没达瓶颈就还能提"的口径一致——12 小时预算内可花的编排手段远没用完。

### 2.2 编排框架的结论（不变，但更笃定）

2026 年的选型资料与本项目教训完全一致，两句被反复引用的话值得直接抄录："如果输入、步骤和输出都固定，模型不需要自己选工具，那么几个函数加一次结构化模型调用就够了"；"多个 Agent 来回发言，Token 一直增加，结果未必比一个函数加一次模型调用更稳"。AutoGen 已进维护模式（微软转向 Agent Framework），LangGraph 1.0 的 durable state / time-travel 对我们是能力过剩。**结论：不引入任何编排框架，保持"纯 Python 编排 + 单模型 OpenAI 兼容调用"的现状，只抄设计模式。** 这与准备二的结论一致，本次调研没有推翻它。

## 三、源码级调研：五个项目各自"最值得偷的东西"

### 3.1 DeepSeek Harness（dsh）——执行日志与压缩的事务化

仓库：`github.com/deepseek-ai/deepseek-harness`（MIT，2026-08-13 开发者预览版，半小时破万 star）。克隆后重点读了 `packages/compaction/`、`packages/subagent/`、`packages/spill/`、`packages/ptc-runtime/`。

**① Surface / Log 双层结构 + 追加式事件日志（最重要）。** dsh 的 Session 是一个 append-only 事件日志：系统提示、思维链、工具调用与结果、子 Agent 调度、每一次上下文注入**全部记录在案**，恢复/分叉/检索/回放共享同一事件流。压缩不是"删历史"，而是一个**事务**（`compaction/start → compaction/summary → user/message(surfaceOp: replace) → compaction/end`）：日志里被替换的原文**永远保留**，模型表面（surface）上用摘要消息替换该区间。任何一次压缩都可以事后审计、甚至回滚。对照我们的 cont_agent：checkpoint 只有 `results` dict，压缩直接重置 messages——**压缩幻觉一旦发生无法察觉、无法回滚**。这是旧系统"压缩幻觉、记忆漂移"问题的现代解法，也是我们事件日志改造的模板。

**② 压缩区间的三条硬不变量**（`compaction-basic/src/region.ts`，601 行，写得非常严谨）：
- `selectCompactableRange`：从尾部往前累计 token 直到 `retainTokens`（最近尾必须**原文保留**），且**绝不切断 tool_call/tool_result 配对**（`toolPairingBalanced`，切断会让模型看到一个没有结果的调用）；
- **收缩校验**：摘要的定价 token 必须**严格小于**被替换内容的 token，否则整个压缩事务失败（"summary is not smaller than the shadowed content"）；
- **稳定性检查**：异步摘要生成期间表面若发生变化，摘要作废重来（`assertSelectedSpanStable`）。

**③ spill-policy：超大工具结果落盘。** 工具结果超过 `maxInlineBytes` 时，全文存入 session 级 spill 文件，模型只看到 head/tail 预览 + 定位符 + 检索指引；且**notice 的字节成本在预算内预留**，保证替换后严格不超上限。`read` 工具豁免（防 read→spill→read 死循环）。对照我们的 `read_novel_lines`：上限 60 行硬截断，没有"落盘 + 定位符"的中间形态。

**④ 子 Agent 的 one-shot / continuable 二分。** 子代理要么一次性（跑完即弃），要么可持续（有 label，父会话可再次投喂）。子代理深度有预算（`SubagentDepthError`），父会话的持久 header 是单调下界——**resume 过的父会话不能按顶层身份再派生**。这直接回答我们"仲裁 agent 该是一次性还是常驻"：**分歧簇仲裁 = one-shot（无状态、干净）；主标注 = continuable（有账本）**。

**⑤ PTC 模式（Code Mode）。** 模型写一段 TypeScript 程序，通过 host 绑定的函数一次编排多轮工具调用，结果以精确 JSON 返回。启发：**结构化批量任务可以让模型"写程序"而不是"多轮对话"**——但对我们收益有限（我们的逐条多轮本身就是有价值的上下文构建），仅作记录。

### 3.2 OpenCode —— prune-first 压缩与"agent 即配置"

仓库：`github.com/sst/opencode`（现 redirect 到 anomalyco/opencode，MIT，188k star）。读了 `packages/opencode/src/session/compaction.ts` 与 agent 体系。

**① prune-first 哲学：先机械回收，再谈 LLM 摘要。** 压缩入口先跑 `prune()`：**从尾部往前保留 `PRUNE_PROTECT = 40_000` token 的工具结果**，更早的已完成工具结果直接标记 `compacted`（内容清除），只有当可回收量超过 `PRUNE_MINIMUM = 20_000` 才动手；序列化进摘要的历史中，**工具输出一律截断 2000 字符**。摘要只保留最近约 **25% 可用窗口**的 turn 作为原文尾。核心思想：**能在代码层确定性回收的，绝不浪费一次 LLM 调用和幻觉风险**。对照 cont_agent：我们直接跳到"LLM 蒸馏成账本"，中间缺了一整层机械压缩——而逐条标注的 user 消息（原文上下文 ±8 行）在 50 条之后完全是冗余的，机械折叠即可。

**② 摘要链（previousSummary）。** 生成新摘要时把上一次摘要作为输入，隐藏旧的 compaction 消息对。这解决"多次压缩信息累积丢失"的部分问题。

**③ agent = 纯配置对象。** `Agent.Info` 是一个声明式 schema：`mode: primary | subagent | all`、`permission`（工具权限规则链）、`tools` 白名单、`prompt`、`model`、`maxSteps`。内置 agent：`build`/`plan`（primary）、`general`/`explore`（subagent）、`compaction`/`title`/`summary`（hidden，专门服务内部任务）。**所有 agent 共享同一个 Session 执行循环**——添加一个新角色 = 加一份配置，零执行逻辑。对照旧系统：每加一个"审阅者"就写一套调用循环、一套恢复逻辑，这正是 17000 行的来源。我们的新 agent 应该是**配置驱动的**（同一段执行循环，不同的 system prompt + 工具集 + max_steps + 上下文构造函数）。

### 3.3 Codex CLI —— 记忆的双阶段管线（对我们最有直接价值）

仓库：`github.com/openai/codex`（Apache-2.0，Rust）。重点读了 `codex-rs/memories/`（README + 模板）与 `history/compaction_checkpoint.rs`。

**① Phase 1（按线程提取）→ Phase 2（全局整合）两阶段记忆管线。** Phase 1 对最近的每个 rollout（会话记录）提取结构化记忆：`raw_memory`（详细）+ `rollout_summary`（紧凑）+ 可选 slug；带**密钥脱敏**、DB lease/claim 防重复、并发上限、失败退避。Phase 2 拿一个**全局锁**，把 stage-1 输出整合成**文件系统渐进式披露记忆**：

```
memories/
  memory_summary.md     ← 永远注入 system prompt（首行版本号，密度优先、可导航）
  MEMORY.md             ← 手册条目，供 grep 关键词
  raw_memories.md       ← Phase 1 合并的原始素材（整合的输入，不是最终态）
  rollout_summaries/    ← 每个历史会话一个蒸馏文件
```

整个 memories 目录是 **Git baseline**：每次整合产出 workspace diff，无变化则 no-op（幂等，"没有值得记的就一个字不改"）。**这套结构几乎就是我们"角色账本"该有的样子**：Phase 1 按卷分段提取角色事件，Phase 2 全局整合成账本文件；账本带版本、可 diff、人工可改；`ledger_summary` 常驻注入，完整账本按需 grep。对照现状：twopass 账本是"一次生成的 JSON"，压缩蒸馏是"每次全量重写"——没有分段素材、没有版本、没有幂等性，错了就一路错下去。

**② 压缩 checkpoint 携带生产者指纹。** `CompactionCheckpoint` 记录 `model_hash`：换模型后旧摘要**不兼容**（显式检查 `is_compatible_with`）。细节但重要——我们如果将来切换模型，历史压缩摘要应作废重建而不是静默沿用。

**③ handoff 摘要的措辞框架。** 压缩 prompt 不是"总结对话"，而是"**为接棒的另一个 LLM 写交接文档**"（进度、关键决策、剩余步骤、必需数据）。摘要前缀明确告知模型"前一个模型已做过这些工作，你可以使用它的工具状态"。我们的蒸馏 prompt 目前只说"合并账本"，没有传达"接棒"语义。

### 3.4 Claude Code —— 四级压缩管线与阈值工程（读逆向文档）

Claude Code 专有，但其源码被社区逆向文档化（deepwiki + 多篇源码分析）。可借鉴点：

| 层级 | 机制 | 我们的对应物 |
| --- | --- | --- |
| L1 Session Memory | 后台持续做增量笔记；压缩时**直接用现成笔记当摘要**，不再让 LLM 通读历史 | 压缩时直接用"最近 50 条折叠表 + 账本"，而非重读全部历史 |
| L2 micro-compact | 无损：删 UI 元数据、过期文件缓存；**工具输出超限截断** | 机械折叠层 |
| L3 full compact | fork 一个 maxTurns=1 的专职 agent 做摘要；压缩后**自动重读最近访问的文件**恢复工作上下文 | 压缩后自动重注入最近 3 条原文上下文 |
| L4 reactive | `prompt_too_long` 强制立即压缩（兜底） | 兜底分支（当前缺失） |

阈值工程：`window − 摘要预留 − AUTOCOMPACT_BUFFER(13k)`；**熔断器 `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3`**——注释直言曾有会话连续失败数千次、全球一天烧掉 25 万次 API 调用。我们旧系统"3126 次模型错误、3984 次结构拒绝"的嵌套重试正是没有熔断的产物。

### 3.5 Plandex / LazyCodex / 记忆层框架 —— 各取一点

- **Plandex**：2M 有效上下文的本质不是大窗口，而是"**每一步只加载该步需要的文件**"+ tree-sitter 全库索引（20M token 代码库的地图）。对我们：仲裁/深查 agent 的上下文应该由编排层**按场景精确装配**（±N 行 + 账本相关条目），而不是粗放地给一大段。
- **LazyCodex (OmO)**（`github.com/code-yeongyu/lazycodex`，3.2k star，MIT）：`$ulw-loop` 的**验证完成**思想——循环跑到"Oracle 验证通过"才算 DONE，不信任模型自报完成；`$init-deep` 生成分层项目记忆；多模型路由按任务难度分配（快任务 mini、难任务高推理）。对我们的映射：**标注条目完成条件 = 格式合法 + 解析通过 + （可选）证据行号在原文范围内**，不满足就重试或降级，而不是接受任意短字符串（D 编号 bug、"说话人"污染的根源）。
- **记忆层框架三阵营**（2026 共识）：向量事实层（Mem0，LOCOMO 93.4%）、时序知识图谱（Graphiti/Zep、Cognee）、记忆 OS（Letta、MemOS）。共同教训：**长期记忆最重要的特性不是容量，而是可修正、可衰减、可审计、可回滚**——"记错了而且越来越确信"是长期 agent 的头号死因。**结论：不引入任何记忆框架运行时**。我们的"实体语义记忆"（角色账本）用**文件系统 + Git**（Codex memories 同路）就是最优解：人类可直接打开修正、可 diff、可回滚、零依赖。

## 四、新编排设计

### 4.0 设计公理（从 30 次实验 + 本次调研提炼）

1. **信息增量公理**：任何拥有改写权的调用，必须拥有比被改写决策**不同的信息来源**（不同上下文窗口、不同证据集、或显式推理模式）。同源重投票已被三次实测证伪（净 -46、-174、0.0pp）。
2. **配置驱动公理**：所有 agent 共享一个执行循环（调用、工具循环、解析、重试、落盘），差异只在配置（system prompt、工具集、上下文构造器、max_steps）。新角色 = 新配置文件。
3. **日志与表面分离公理**：一切进模型上下文的内容由事件日志投影而来；压缩/裁剪只改变表面，永远不删日志。任何决策可回放。
4. **机械优先公理**：能用确定性代码做的（折叠、截断、检索、黑名单解析、分歧检测），绝不用模型。
5. **幂等与可回退公理**：每个阶段产物落盘 + 版本化；重跑该阶段是 no-op 或纯增益；任何层可关闭后回退到上一层产物。

### 4.1 Agent 分工总表

| # | Agent（配置名） | 模式 | 职责 | 上下文构造 | reasoning | 预估调用量/卷 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `ledger_extract` | one-shot × N 段 | 按 2000 行分段提取角色事件：canonical 名 / 别名 / 泛称 / 首现行号 / 身份揭示点 / 关系 | 段原文（~2.5 万 token） | none | ~15 次 |
| 2 | `ledger_merge` | one-shot | 把 N 段产物整合成 `ledger.md` + `ledger_summary.md`（幂等，产出 diff） | 全部段产物 | none | 1–2 次 |
| 3 | `annotator_seq`（主通道 A） | continuable | 逐条连续标注：交替追踪 + 账本 + 工具查证 | system + ledger_summary + 最近 40 条原文对话 + 折叠表 | none | ~1450 次 + 工具 ~10% |
| 4 | `annotator_vol`（主通道 B） | one-shot | 整卷 + 账本 + 强制证据引用（`evidence_annotate --with-ledger` 现成） | 整卷 9.5 万 token + 账本 | none | 1 次 |
| 5 | （无模型）`diverge` | — | 纯 Python：对比 A/B 输出，产出分歧簇（按场景聚类，同簇连续 D 编号） | — | — | 0 次 |
| 6 | `arbiter` | one-shot × 簇 | 分歧仲裁：给双方答案 + 双方证据行 + ±30 行原文 + 账本，判决并输出裁决依据 | 簇上下文（精确装配） | **high** | ~200 簇 × 1 |
| 7 | `hardcase`（深查） | one-shot × 簇 | 双错条目场景块深查：±50 行 + 账本 + `read_novel_lines` 深查预算（每块 ≤8 次工具）+ 证据强制 | 场景块上下文 | **high** | ~60 块 × 3–8 |
| 8 | `nonperson_gate` | one-shot × 簇 | 只对"双方都给人物但引语可疑"的条目做 precision-first 二次确认（判据：无引导动词 / 超短 / 元语言标记），仅高置信才改判 | 引语 + ±10 行 | high | ~50 次 |
| 9 | `normalizer` | one-shot | 输出词表归并（身份消解）+ 空标签用通道 B 填补 | 输出词表 + 账本 | none | 1–2 次 |
| 10 | （无模型）`auditor` | — | 纯 Python：每阶段对照冻结答案打分，产出 修复/回归/净收益 报告（只统计不改写） | — | — | 0 次 |

关键点：

- **agent 3 与 4 就是已被验证的 92.31% + 91.47% 双通道**，本方案不推倒它们，而是在其后加 5/6/7/8 四个"信息增量层"；
- **每个新层的改写范围都被严格收窄**（只碰分歧簇 / 双错簇 / 可疑引语），保护 6075 条双对样本——这是"强制引用证据"99.21% 保护率的教训延伸；
- 仲裁 agent 拿到的是**两个不同上下文产生的判断 + 各自证据**，这构成第 3.1 节公理要求的信息增量，与旧系统"同一模型近似 prompt 投五票"有本质区别。

### 4.2 一次处理多少（批大小）

| 单位 | 大小 | 依据 |
| --- | --- | --- |
| 账本提取段 | 2000 行（~2.5 万 token） | 单次调用可完整容纳，段边界选在场景/章节空行处（机械） |
| 主通道 A 标注单位 | 1 条/轮（不变） | 交替追踪需要连续性，已验证 |
| 仲裁簇 | 3–10 条连续分歧（同场景） | 同簇共享上下文与证据，一次判决减少 4–5 倍调用；簇内每条单独输出 |
| 深查场景块 | ±50 行内全部相关 D | 场景完整性（准备六证伪过 ±12 行窄窗） |
| 折叠表粒度 | 50 条/块 | 对齐 checkpoint 周期，机械可算 |
| 压缩触发 | `prompt_tokens > 600k`（沿用） | 1M 窗口 60% 安全余量，已验证 |

### 4.3 时间预算核算（单卷 ≤ 12h 的验收）

以实测吞吐（单卷跑约 13 条/分钟；五卷并行时每卷 ~2.3 条/分钟）计算：

| 阶段 | 调用量 | 单卷时间（串行估算） |
| --- | --- | --- |
| 账本两阶段 | ~16 次 | ~15 min |
| 通道 A（逐条） | ~1450 次 | ~3.5 h（实测） |
| 通道 B（整卷） | 1 次 | ~3 min |
| 仲裁（~200 簇，开推理） | ~200 次 | ~2 h |
| 深查（~60 块 × 5） | ~300 次 | ~1.5 h |
| 引语二次确认 + 归一 | ~52 次 | ~20 min |
| **合计** | | **~7.8 h < 12 h** ✅ |

留 4 小时余量给限流冷却、重试与人工抽查。**注意**：五卷并行会触发模型池 cooldown（实测降到 2.3 条/分钟），所以建议**卷间错峰**（同时最多 2 卷在"逐条"阶段，仲裁/深查阶段可并行），这本身也是编排问题，写进调度器即可。

### 4.4 每类 Agent 的多轮上下文形态

- **`annotator_seq`（唯一的长会话）**：`system(铁律+口径) → ledger_summary → [折叠表×k] → 最近 40 条原文对话 → 当前条`。压缩后**自动重注入最近 3 条的原文上下文**（Claude Code L3 的"压缩后重读文件"），防止压缩瞬间丢失局部交替状态——旧系统"压缩幻觉 + 连续错位"的直接对策。
- **`arbiter` / `hardcase` / `nonperson_gate`**：短会话（1–8 轮），每次一个簇/块，**无跨簇记忆**（防污染），账本以只读摘要注入。
- **`ledger_extract` / `merge` / `normalizer`**：单轮调用。

### 4.5 工具调用设计

| 工具 | 归属 | 设计要点（借鉴来源） |
| --- | --- | --- |
| `read_novel_lines(start, count)` | annotator_seq / hardcase | ① 保留 60 行硬上限；② 结果超 2000 字符时改为 head/tail 预览 + 精确行号区间（OpenCode 截断 + DSH spill 思想），需要时模型可精确再读；③ 结果进日志全文、进表面截断 |
| `search_novel(pattern, k)`（新增） | hardcase / ledger_extract | 正则/字面检索角色名与泛称，返回 (行号, 行文本) 列表——**纯机械检索交给代码**，省模型 token 与幻觉 |
| `get_ledger(query?)`（新增） | 全部 | 只读账本（摘要或按角色 grep），账本是文件 |
| `propose_ledger_update(entry, evidence_lines)`（新增） | annotator_seq | 账本更新走**提议**而非直写：编排层校验 evidence_lines 真实存在且包含该名字，append 进日志，Phase 2 式整合时采纳（防"记忆漂移"：模型不能凭空发明角色） |
| 解析黑名单 | 编排层 | 沿用 `PROMPT_WORD_BLACKLIST` + 拒绝 D 编号/行号回显；**完成条件前置校验**（LazyCodex 验证完成思想）：标签 ∈ 账本 ∪ 泛称白名单 ∪ {无人称引语}，否则该轮无效并带错误反馈重试 |

全部工具**只读**（除账本提议走日志），答案文件物理隔离在任何 agent 的工作目录与工具可达范围之外。

### 4.6 记忆层设计（五层）

| 层 | 载体 | 读写者 | 失效/修正机制 |
| --- | --- | --- | --- |
| L1 工作记忆 | 当前会话 messages | 执行循环 | 每轮重建 |
| L2 事件记忆 | `events.jsonl`（追加式：call/tool/compaction 事务/ledger 提议） | 执行循环写，auditor 读 | 只追加不修改；回放可重演任何决策 |
| L3 语义记忆 | `ledger.md`（canonical/别名/泛称/揭示时间线/关系） + `ledger_summary.md` | ledger_extract/merge 写，全员读 | Git 版本化；提议-校验-采纳管线；人工可改 |
| L4 关系记忆 | ledger 关系字段 + 分歧簇记录（`divergence/clusters.json`） | diverge/arbiter | 随 L3 版本化 |
| L5 反思记忆 | `docs/pitfalls.md`（"短引语易误判 B"、"交替规则在叙述打断处失效"……） | 人 + 实验复盘写，prompt 注入 | 每次全卷复盘更新；防对五卷过拟合的部分靠"泛化卷"验证 |

要点：**L3/L4 全部是文件 + Git**（Codex memories 路线），不引入 Mem0/Letta 任何运行时；蒸馏只允许"合并别名、记录身份揭示、补充有行号证据的新说话人"（CowAgent Deep Dream 的合并/萃取/冲突更新 + DSH 不变量思想）。

### 4.7 上下文压缩设计（三级管线 + 兜底）

```
触发顺序（每次调用后检查 usage.prompt_tokens）：
  > 450k → ① 机械折叠（无 LLM）：把 >50 条前的逐条 user/assistant 对折叠成
           "D0001–D0050: 罗伦斯×31, 赫萝×15, 无人称引语×4 [表格]" 一条消息
           （OpenCode prune-first：确定性回收优先，零幻觉）
  > 600k → ② LLM 蒸馏（事务化）：compaction/start 记日志 → 蒸馏成账本增量 +
           handoff 摘要（Codex 措辞：给接棒者的交接文档）→ 收缩校验（摘要
           token 必须小于被替换区间）→ compaction/end；失败则保留原状重试，
           连续失败 3 次熔断（Claude Code），降级为"只折叠不蒸馏"
  兜底   → ③ reactive：收到超限错误 → 丢弃最老折叠块 + 重注入最近 3 条原文 → 重试
```

不变量：折叠/蒸馏**永不切断**"当前条目的原文上下文"与其标注结果的配对；最近 40 条对话**永远原文保留**；每次压缩后自动重注入最近 3 条的原文。

### 4.8 预期收益核算（诚实版）

| 增量层 | 目标条数 | 假设 | 预期净增 |
| --- | --- | --- | --- |
| 分歧仲裁（731 条分歧） | cont 对 395 / ev 对 336 已知 | 仲裁正确率 ≥60%（高于盲信多轮的 54%）；带证据对比 + 高推理有可能到 65–70% | +40~110 条（+0.6~1.6pp） |

## 六、明确不做的事

## 九、一句话总结

**旧系统用 15–18 次/条的调用证明了"编排能补偿模型"，但它把预算花在了同源重投票上；新方案用 12 小时预算里剩下的 8.5 小时，只购买三种已被证明存在的信息增量——两条互补通道的分歧、对分歧与双错的高推理深查、以及一份可审计可回滚的文件化角色账本——预期 94.4% 左右追平旧系统，并让 95% 的可能性交给"203 条真难点 × reasoning 深查"去裁决。**
