## 0. 结论摘要（先说答案）

1. **同意你的判断：瓶颈在编排，不在模型。** 数据支撑：旧系统用远弱于 v4-flash 的模型 + 重编排 = 94.19%；新系统强模型 + 薄编排 = 92.77%；单卷预算 12h 只用了 3.5h，**还有约 3.4 倍的编排空间没花**。Anthropic 的多 agent 研究系统数据也佐证：agent 任务性能方差的 80% 由 token 消耗量解释——我们的问题恰恰是「该花 token 的地方（分歧裁决）没花」。
2. **差距的量化结构**：92.77% → 95% 需要再对约 160 条。三个来源：① 731 条两方案分歧条目（约 146 条/卷）——裁决器是主战场；② 203 条共同盲区——需要「新视角 pass」制造分歧再裁决；③ 后处理归一（已兑现 +0.46pp）。
3. **裁决器精度是唯一的生死参数**：在 731 条分歧上，当前「信多轮」= 54% 命中；裁决器需 ≥75% 才能把总分推到 ~95%（量化见 §6）。`refine_divergent.py`（正在跑的推理重标）本质上就是裁决器原型，它的结果直接校准这个参数。
4. **架构上不要再造旧系统**：新系统应该是「确定性 Python 编排 + 少量角色化 LLM agent + 分层压缩 + 事件日志」，总量控制在 ~1500 行以内。旧系统 17K 行的死因（每层审阅都有改写权、同源投票、审阅器信息少于标注器）在调研的外部文献里全部有对应反例（MAST 失败分类、agreement bias、correlated failure），我们的学费和业界结论完全一致。
5. **外部工具结论**：没有现成框架值得整体引入（TypeScript/Rust 生态、为 coding 场景设计），但**七个具体机制值得抄**：Codex 的 handoff 压缩提示词、OpenCode 的 prune-first 压缩顺序、Claude Code 的五层压缩 + 子代理隔离、DeepSeek Harness 的 append-only 事件日志与「描述符不参与压缩」、Letta 的 sleep-time 记忆整理、SWE-agent 的 ACI 工具设计四原则、LuckyD Code 的 DeepSeek 栈工程细节（reasoning_content 计入 token 估算、15% 分词安全系数、孤儿 tool 消息清理——见 §3.11，用户所指的「luckycode」）。每个都给出了源码位置。

## 1. 现状差距结构（数据复盘）

对 7009 条的已知分解（来自重构准备八）：

| 情形 | 条数 | 占比 | 含义 |
| --- | ---: | ---: | --- |
| 多轮 & 整卷都对 | 6075 | 86.7% | 共识区，**任何审阅机制都不得触碰** |
| 仅多轮对 | 395 | 5.6% | 当前「信多轮」的收益来源 |
| 仅整卷对 | 336 | 4.8% | 被丢弃的正确信号 |
| 两方案都错 | 203 | 2.9% | 共同盲区，旧系统也 0 对 |

设分歧集合（731 条）上最终命中率为 A，盲区 203 条上恢复率为 r，则总分：

```
总分 ≈ (6075 + 731×A + 203×r) / 7009
当前 A=0.54（信多轮）, r=0 → 92.31%（+归一后 92.77%）
A=0.70, r=0     → 93.98%
A=0.75, r=0.10  → 94.72%（+归一≈95.2%）✅ 目标线
A=0.80, r=0.10  → 95.24%
A=0.65, r=0     → 93.45%（不合格，但+归一≈93.9）
```

三个推论：

1. **共识区神圣不可侵犯**。多轮与整卷一致且本来就对的部分回归率 99.21%（引用机制的核心价值）。任何「再审一遍」的机制（旧系统 scene-review 净改坏 174 条的教训）都是负期望。新架构里审阅类 agent 只在「存在分歧」时被创建。
2. **分歧条目上 54%→75% 是一个可达但需要设计的目标**：这些条目至少有一个 pass 是对的，且都带证据行号——裁决不是开放题，是「二选一/三选一 + 证据核验」的受限选择题。这正是我们已证伪的「同源投票」做不到、但「信息结构多样化 + 深查证据」可能做到的（原理见 §3.9 测试时扩展与 §3.10 相关性失败研究：多样性必须来自任务分解与信息结构，不能来自采样）。
3. **盲区 203 条是新视角 pass 的专属目标**。两方案同错说明「整卷一次读」和「正向逐条读」这两个视角都不够，需要第三个正交视角（场景块批量读 / 逆向读 / 对话链重构 / 无人称引语专职判定）先制造分歧，再走同一裁决通道。

## 2. 新架构总览

```
                        ┌────────────────────────────────┐
                        │  Orchestrator（纯 Python，无 LLM）│
                        │  确定性流水线 + 事件日志 + 断点续跑  │
                        └───────────────┬────────────────┘
                                        │
  Pass 0（每卷一次）                     │      Pass 1/2/3（可并行）
  ┌─────────────────┐                   │   ┌──────────────────────────┐
  │ Ledgerist 账本员  │──ledger.json──▶──┼──▶│ A 整卷证据标注器（已有）      │
  │ 整卷→角色账本      │                   │   │ B 连续多轮标注器（已有）      │
  └─────────────────┘                   │   │ C 场景块批量标注器（新增）    │
           ▲                            │   └──────────┬───────────────┘
           │ sleep-time 整理             │              ▼
  ┌────────┴────────┐                   │   ┌──────────────────────────┐
  │ Sleeper 睡眠整理员 │◀──事件日志(JSONL)──┤   │ Divergence 分歧检测（纯代码）│
  │ 异步重整账本+锚点   │                   │   │ 共识→直接输出；分歧→进裁决    │
  └─────────────────┘                   │   └──────────┬───────────────┘
                                        │              ▼
                                        │   ┌──────────────────────────┐
                                        │   │ Arbiter 裁决器（reasoning=high）│
                                        │   │ 受限选择+证据核验，批量会话     │
                                        │   └──────────┬───────────────┘
                                        │              ▼
                                        │   ┌──────────────────────────┐
                                        │   │ Normalizer 后处理（归一/兜底） │
                                        │   └──────────────────────────┘
```

设计的第一原则来自 MAST 失败分类（§3.10）：**协调层绝不使用 LLM**。编排、分歧检测、checkpoint、合并规则全部是确定性 Python；LLM 只出现在「读小说、做判断」的角色里。旧系统一半的复杂度（场景仲裁、晋级聚合、多路转换门槛）本质上是在用 LLM 做协调层的事情。

## 3. 外部调研：2026 年 Agent 工具生态

> 方法说明：以下每个项目都做了「克隆 → 读关键源码文件」或「读官方工程博客/论文」至少其一；「我读过的源码位置」均在本地 `tmp/agent_ref/` 可复查（ref_codex / ref_opencode / deepseek-harness，克隆于 2026-09-21）。

### 3.1 OpenAI Codex CLI（Rust）——压缩是一门「任务」

- 仓库：https://github.com/openai/codex （Apache-2.0，克隆时最新 commit 2026-09-21）
- **我读过的源码**：`codex-rs/core/src/compact.rs`、`compact_token_budget.rs`、`codex-rs/prompts/templates/compact/prompt.md`
- 关键机制：
  - 压缩被建模为**一等公民任务**（`run_compact_task`），带 pre/post hook、analytics、成败追踪，而非循环里的一个分支；
  - 压缩提示词是「给下一个 LLM 的交接摘要」（handoff summary），要求包含：进度与关键决策、约束与偏好、剩余步骤、继续所需的关键数据——**不是「摘要对话」而是「写交接文档」**；
  - `COMPACT_USER_MESSAGE_MAX_TOKENS = 20_000`：送进压缩调用的用户消息封顶，防止压缩请求本身爆窗；
  - `InitialContextInjection` 区分「轮前压缩」（下轮完整重注入初始上下文）与「轮中压缩」（把初始上下文注入到压缩摘要之后、最后一条 user 消息之前）——因为模型被训练成期望压缩摘要在特定位置；
  - token-budget 变体（`compact_token_budget.rs`）甚至**跳过模型摘要直接开新窗口**，但仍然走完整压缩生命周期，保证 hook 和事件可见性。
- **对本项目的借鉴**：我们当前的 distill 提示词是「合并账本 JSON」，信息保留维度太窄。应改成 Codex 式 handoff：`账本 + 场景进度（标到哪了、当前在什么场景、谁在场）+ 已确定的判决与依据 + 待办`。

### 3.2 OpenCode（sst）——prune-first：能用字符串解决的不调模型

- 仓库：https://github.com/sst/opencode （MIT，克隆时最新 commit 2026-09-21 08:40）
- **我读过的源码**：`packages/opencode/src/session/compaction.ts`（完整通读）
- 关键机制（源码常量，非转述）：
  - `PRUNE_MINIMUM = 20_000`、`PRUNE_PROTECT = 40_000`、`TOOL_OUTPUT_MAX_CHARS = 2_000`；
  - **prune 阶段**：从后向前扫，保护最近 2 个 user 轮和 skill 类工具结果，累计 40K token 以内的工具输出不动，超出部分的老工具结果标记 compacted（渲染为 `[Old tool result content cleared]`），**只有可回收量 > 20K 才真正执行**——避免无意义的反复改写；
  - **summarize 阶段**：溢出时用隐藏的 `compaction` agent（禁用所有工具、专用 126 词提示词）生成摘要；尾部保留预算 = `clamp(可用窗口×25%, 2K, 15K)`，按完整 turn 回溯，放不下时**在 turn 内部找切分点**而不是丢弃整个 turn；
  - 摘要提示词带结构（Goal / Instructions / Discoveries / Accomplished / Relevant files）且**链式携带上一次的摘要**（`previousSummary`），多轮压缩不丢早期信息；
  - agent 的本质是「配置 + 权限规则集」：plan 模式 = `edit: deny`，explore 子代理 = 只放开 7 个只读工具——**模式不是代码分支，是规则集**。
- **对本项目的借鉴**：① 压缩顺序必须是「先免费后付费」：先清老工具结果、再截断旧轮、最后才蒸馏；② 我们当前 600K 一刀切蒸馏，等于每次都直接上最贵的手段；③ 每条 user 消息重复格式约束（已踩过的格式漂移坑）与 OpenCode 的 reminders 机制同理。

### 3.3 Claude Code——五层压缩与子代理隔离

- 官方文档（子代理）：https://code.claude.com/docs/en/sub-agents ；社区逆向分析的压缩管线：https://soviar-systems.github.io/ai_engineering_handbook/claude-code （及 http://quidproquo.cc/posts/ai/2026-08-25-coding-agent-context-compaction-en ，后者对 pi/omp/opencode/codex/claude-code 五家压缩实现做了源码级横评）
- 关键机制：
  - 五层压缩（由便宜到贵）：Tier1 工具结果预算裁剪 → Tier2 Snip（整块删除老消息但保持 tool_use/tool_result 原子对）→ Tier3 Microcompact（只清 COMPACTABLE_TOOLS 集合里的旧工具结果）→ Tier4 Context Collapse（读时投影，不改原始历史，不毁 KV cache 前缀）→ Tier5 Auto-Compact（真调模型做 9 段结构化摘要，触发阈值 = 窗口 − 13K token）；连续 3 次压缩失败触发熔断器永久禁用自动压缩（历史上曾因压缩死循环浪费 25 万次调用/天）；
  - 子代理四价值：**上下文隔离**（中间过程留在子代理，只回传结论）、并行、专用指令、工具白名单；「需要无偏分析时明确要求 fresh context 子代理」；
  - 压缩后回注（post-compact restore）：最近读过的 5 个文件（50K 预算）重新注入。
- **对本项目的借鉴**：裁决器天然就是「fresh-context 子代理」——它不该继承标注器的对话历史（会带入标注器的偏置），只该拿到：账本 + 两个候选答案 + 各自证据行号 + 查原文工具。这正是 Claude Code 子代理「隔离即去偏」的用法。

### 3.4 DeepSeek Harness（deepseek-ai，2026-08-13 开发者预览）——一切皆插件 + 运行有迹可循

- 仓库：https://github.com/deepseek-ai/deepseek-harness （MIT）；官网 https://www.deepseek.com/harness/en/
- **我读过的源码**：`packages/compaction/compaction-tool-result-pruner/`、`packages/spill/`、`packages/subagent/subagent/`（含 README 与 src 目录结构；克隆时最新 commit 2026-09-17）
- 关键机制：
  - **append-only 会话日志**：模型看到的一切（系统提示、思维链、工具调用与结果、子代理调度、每次上下文注入）都写入仅追加的事件流；恢复、分叉、检索、回放共享同一份流。这是「Everything is a plugin」之外最值得抄的工程决定；
  - **tool-result-pruner**：超 8192 字符的工具结果 → 保留头 4096 + 中间剪除标记 + 尾 1024，纯字符操作零模型调用，**原始结果留在日志里可回放**；修剪后若压力解除则跳过摘要；
  - **spill**：超大文本落盘换「定位符 + 预览」，`maxInlineBytes` 之上自动降级为 preview+locator；
  - **subagent**：one-shot（跑完即毁、返回最终结果）与 continuable（持久会话、可继续对话）两种形态；`maxDepth` 默认 1 防递归；**子代理描述符是日志事件、不进模型历史、压缩时保留**——子代理的存在不会污染上下文。
- **对本项目的借鉴**：① 事件日志：每条标注的「模型看到了什么、调了什么工具、为什么这么判」全部 JSONL 落盘——这直接解决「203 条盲区归因难」的问题（现在只有结果没有轨迹）；② 工具结果头尾保留修剪；③ 裁决器用 one-shot 子代理形态，账本整理用 continuable 形态。

### 3.5 Letta（MemGPT 后继）——记忆分块 + sleep-time compute

- 仓库：https://github.com/letta-ai/letta ；**注意：其 Python 服务端已归档到 `archive` 分支，现役源码迁至 TypeScript 的 https://github.com/letta-ai/letta-code **（我克隆了 letta 主仓确认，README 明示）；sleep-time compute 博客：https://www.letta.com/blog/sleep-time-compute ；论文 https://arxiv.org/abs/2504.13171
- 关键机制：
  - 记忆三层：core memory（in-context 可编辑分块，如 persona/character 块）、recall memory（对话史检索）、archival memory（归档检索）；模型通过 `core_memory_append/replace` 工具自己维护核心记忆；
  - **sleep-time compute**：一个后台「睡眠 agent」与主 agent 共享记忆块，在空闲期重整主 agent 的上下文（合并、萃取、冲突消解），主 agent 不需要承担记忆维护的调用开销。论文数据：同等精度下测试时计算可降约 5 倍，或同等预算下精度最多 +13~18%；
  - 记忆整理与对话解耦后，**睡眠 agent 可以用更强配置**（不受延迟约束）。
- **对本项目的借鉴**：账本维护从标注循环里拿出来，交给异步的 Sleeper：B/C pass 边跑边产生原始记录，Sleeper 在旁边（或 pass 间隙）重整账本（别名合并、身份揭示回填、冲突记录）。当前 cont_agent 在压缩时才临时 distill 一次账本，信息密度低且打断主线；改为持续后台重整。注意 sleep agent「不受延迟约束」正好对应我们可以给它 reasoning_effort=high（批量主流程必须 none 的平台约束不冲突）。

### 3.6 Mem0——分层记忆与「写入只增、冲突在检索时解决」

- 官网 https://mem0.ai ；graph memory 文档 https://docs.mem0.ai/platform/features/graph-memory ；论文（LOCOMO 基准）https://arxiv.org/abs/2504.19413
- 关键机制：记忆分层（会话内/会话/用户/组织四层作用域）；提取阶段 **ADD-only**——新事实不覆盖旧事实，矛盾双方都保留，**在检索时用 recency+relevance 排序决定谁浮出**；graph 变体自动抽实体做节点、共享实体的记忆自动连边，实体中心查询获得排序加权。
- **对本项目的借鉴**：账本不要在写入时就「合并掉」旧别名（当前 distill 是破坏性合并，一旦合错无法回溯）；改为 append-only 记录 + 检索时排序。角色账本天然是 graph：节点=canonical 名，边=别名/同现。泛称归一失败过的「错绑」问题本质就是写入时破坏性合并。

### 3.7 SWE-agent——ACI（Agent-Computer Interface）设计四原则

- 论文 https://arxiv.org/abs/2405.15793 （NeurIPS 2024）
- 四原则：**动作简单易理解；动作紧凑高效（一个动作顶多个）；反馈信息量大但简洁；护栏防止错误传播**。消融数据：搜索接口汇总化（返回文件名+命中数而非全文）+6pp；编辑器带 lint 护栏 +3pp；100 行文件窗口优于 30 行和全文件；历史折叠 +3pp。核心洞察：**LM 是一类新用户，工具接口要为它重新设计，不能照搬给人的 Unix 工具**。
- **对本项目的借鉴**：见 §5 工具设计。我们现有的 `read_novel_lines` 已符合「紧凑+有界」，缺的是「汇总式搜索」和「护栏式反馈」。

### 3.8 Anthropic 多 agent 研究系统——token 解释 80% 的性能方差

- 工程博客：https://www.anthropic.com/engineering/multi-agent-research-system
- 关键数据与结论：orchestrator-worker 模式（lead 规划+分派，subagent 并行检索）；**token 消耗量单独解释 BrowseComp 性能方差的 80%**；多 agent 比聊天贵约 15 倍 token，只配用于高价值任务；「教 lead 怎么分派」（目标、输出格式、工具指引、边界缺一不可）；「按查询复杂度伸缩投入」写入提示词。
- **对本项目的借鉴**：① 我们 12h 只用 3.5h，等于「该花的 token 没花」；② 分派必须显式定边界（旧系统审阅器「不知道标注器知道什么」就是边界缺失）；③ 按条目难度分配计算——共识条 0 额外调用、分歧条 1 次深查、盲区条多视角重标，这就是 compute-optimal 的任务版。

### 3.9 测试时扩展（Test-Time Scaling）——「超额路径」与「计算最优分配」

- The Path of Excess（Berkeley SkyLab）：https://arxiv.org/abs/2509.09674 —— 核心发现：在无验证器的开放任务上，**用多样化 scaffold 重复采样 + 聚合**能持续提升（Code Tropes 上 60%→80%@4096 次），且聚合器的鲁棒性比采样器更强；单次成功率与 pass^k 的差距主要来自 scaffold 多样性而非模型随机性。
- Compute-optimal（Snell et al., ICLR 2025）：https://arxiv.org/abs/2408.03314 —— 按题目难度自适应分配测试时计算，比统一 best-of-N 效率高 4 倍以上。
- Sample, Scrutinize and Scale（Google, ICML 2025）：https://arxiv.org/abs/2504.02495 —— 「在候选间比较」本身产生关于错误位置的信号，是比单答自验证更好的验证方式。
- **对本项目的借鉴与警告**：⚠️ 这条线**不能**直接搬「同 prompt 重复采样」——我们已实测温度采样塌到 50%、同源投票 ≈0（与 §3.10 的相关性失败研究一致）。Path of Excess 的有效成分是 **scaffold 多样性**：不同 pass = 不同 scaffold（整卷读 / 逐条读 / 场景块读 / 逆向读），错误相关性低（我们自己的数据：336 vs 395 独对，已经是证据），然后聚合器（裁决器）做「比较与选择」——这正是 Sample-Scrutinize-Scale 说的「比较即信号」。

### 3.10 多 agent 系统的失败研究——我们的学费清单业界已付过

- MAST 失败分类（Why Do Multi-Agent LLM Systems Fail?）：https://arxiv.org/abs/2503.13657 —— 1600+ 条轨迹、14 种失败模式；**规格不清 41.8%**，模型质量不在头部失败原因里。失败主要发生在协调层，不在模型层。
- Agreement bias（沉默的一致性）：https://arxiv.org/abs/2505.21503 —— 多 agent 讨论过早收敛于错误共识；解法是「鲶鱼 agent」结构性唱反调。另有 ICML 2026 工作（Okawa et al.）证明多 agent 辩论系统性收敛到偏置共识、互相强化而非纠错。
- Correlated failure：https://synapsesocial.com/fr/papers/6a9d1eb628139818eab21bd1 —— 推理模型的成对错误相关性（φ≈0.57）显著高于非推理模型；共识投票在单体正确率 <50% 时反而放大失败（59.4%→67.4%）。
- Cognition《Don't Build Multi-Agents》及后续实践：https://cognition.ai/blog/dont-build-multi-agents —— 实践结论：多 agent 有效的形态几乎都是**只读子代理**（搜索、调研），写路径保持单线程。
- **对本项目的映射**（逐条对应我们付过的学费）：

| 业界结论 | 我们对应的实验 | 学费 |
| --- | --- | --- |
| 同源投票无独立信号 | 4 方案多数投票、温度×5 采样 | ≈0 收益 / 塌到 50% |
| 审阅者信息少于执行者却有改写权 → 净负 | 7-16 场景审阅、7-26 整段场景 | 净改坏 46 / 174 条 |
| 过早收敛（agreement bias） | 旧系统镜像陪审（同模型多职责） | 十几天换 94.19% |
| 失败在协调层不在模型 | 三阶段流水线误差不可逆传导 | v6 三卷变差 |
| 只读子代理是有效形态 | （新启示）裁决器应为只读+受限选择 | 待验证 |

### 3.11 LuckyD Code（用户所指的「luckycode」）——同技术栈、同规模的单人 agent 参考

- 项目身份：PyPI 包 `luckyd-code`（1.2.2，MIT，DeepSeek API 驱动，deepseek-v4-flash/pro 两档模型），作者 Dylanchess0320，2026 年发布；终端 CLI + FastAPI Web UI 双形态，定位即「Claude Code 的开源平替」（Claude Code 闭源）。**注意现状**：GitHub 主仓 `Dylanchess0320/LuckyD-Code` 已删除（404，作者名下现存仓库仅 `LuckyD-Browser`，2026-09-19 更新，其 SYSTEM_PROMPT 仍写着 "You are LuckyD Code"——即同一项目演进为「AI 浏览器 + coding agent」形态）；源码我直接从 PyPI 下载 sdist 阅读，演进版 LuckyD-Browser 也已克隆对照。
- **我读过的源码**（sdist 解包于本地 `tmp/agent_ref/pypi_luckyd/`，1.2.2 版）：`context.py`（214 行全文）、`router.py`（417 行全文）、`_agent_loop.py`（551 行全文）、`verify.py`（360 行全文）、`orchestrator.py`（204 行全文）、`memory/manager.py`（339 行全文）、`brain/retriever.py`（234 行全文）、`api.py` 的 `_repair_json`、`planner.py`/`self_improve.py` 头部协议、`background.py`；演进版 `ref_luckyd_browser/core/checkpoint.py`（文件级快照，明注借 Cline 模式）。
- 关键机制（按我们的六个设计问题映射）：
  - **统一 agent 循环**：单一 `run_agent_loop()` 被 CLI、Web UI、SubAgent、AgentHandoff 四处共用（"Fix a bug there and it propagates everywhere"），循环是 Think → Act → Verify → Recover 四段；Coordinator 流水线 = researcher + tester 并行 → coder → reviewer，角色 prompt 仅 4-6 行（角色定义轻量化）；
  - **子代理上下文**：SubAgent/AgentHandoff 均为**全新 ConversationContext（max_messages=20）**，只拿 task 描述不继承主对话（与 DSH one-shot、Claude Code 隔离一致，三家互证）；handoff 间传参截断 1500 token（研究结论 → coder 的上下文预算控制）；
  - **工具设计**：只读工具并行（≤4 线程）、写工具串行（`WRITE_CONFLICT_TOOLS` 集合防竞态）；工具结果截断 8000 字符（头 4000 + 尾 2000 + 修剪计数提示，与 DSH pruner 的 8192=4096+1024 同构互证）；Write/Edit 后 re-read-after-write；**卡死检测**（连续 3 次相同「工具名+参数」md5 → 注入打破消息）；`_repair_json` 的所有 JSON 修复**只在字符串字面量之外进行**（逐字符跟踪 in_string + escape 状态），删尾逗号、补未闭合括号，不破坏含 `}`/`,` 的合法字符串值；
  - **压缩**：阈值 800K（1M 窗口留 200K 余量），**每轮开始前 0.85×阈值就提前触发**；tiktoken cl100k_base + **15% 安全系数**（DeepSeek 分词器与 OpenAI 不同的补偿）；**reasoning_content 计入 token 估算**（源码注释原话：DeepSeek 思考块 "hundreds of tokens per assistant turn" 曾对压缩阈值不可见）；压缩 = flash 模型摘要（"summarisation doesn't benefit from the Pro model"）+ system + 摘要 + keep_last=8；修剪后**孤儿 tool 消息清理**（tool 消息必须仍配对 assistant tool_calls，否则 DeepSeek API 直接报错）；handoff 时系统提示**拼接为单个 system 消息**（DeepSeek 不支持连续两个 system 轮）；
  - **记忆层**：文件即记忆（`{type}_{name}.md` + MEMORY.md 索引）；双模降级检索（sentence-transformers 语义，score>0.1 过滤 → 关键词频率兜底）；嵌入模型单例（加载 1-3s/90MB，双检锁，每进程一次）；`<memories>` XML 注入每条截 500 字符；会话摘要 = latest 快照 + append-only 日志双层；`brain/` 检索器四级降级：**RRF 融合（向量+BM25，K=60）→ 向量单路 → BM25 单路 → 图关键词兜底**；
  - **验证与恢复**：verify.py 五段管线（syntax 必跑且失败短路 → lint → AST 一致性 → test → task），每个 `VerificationResult` 自带 **fix_hint 修复指引**并格式化回注模型；验证失败 → 反馈 → 重试（≤3 次）→ **中途升模型**（`_ESCALATION_LADDER: flash → pro`）；**轮次预算警告**（剩 ≤2 轮注入收尾指令，标志位防重复注入）；测试命令白名单防 shell 注入；模型路由 4 档，LLM 分类器零阻塞（`future.result(timeout=0.01)` 几乎必超时 → 即返启发式，后台线程算完写缓存供下次命中），工具调用 ≥2 次升 1 档、≥8 次升 2 档。
- **对本项目的借鉴**（这是全部调研里「技术栈同构」最高的参考——同为 Python + DeepSeek + 单人开发）：
  1. **三个 DeepSeek API 实操坑直接记录**：reasoning_content 要计入 token 估算（我们 Sleeper/Arbiter 开 reasoning 时必踩）、修剪后孤儿 tool 消息清理、单 system 消息约束——这些在 Codex/OpenCode（OpenAI/Anthropic 栈）的源码里根本看不到；
  2. **15% 安全系数 + 0.85 提前量**：我们的 600K 阈值判断可加上这两层（当前是「到点才压、估算零余量」）；
  3. **effort 升级阶梯代替模型升级阶梯**：他们 flash→pro，我们对应 none→low→high（reasoning_effort），「验证失败中途升档」改成「分歧/解析失败中途升 effort 重标」；
  4. **fix_hint 机制**：Arbiter 输出无效（JSON 解析失败、候选越界）时的错误反馈应自带「怎么改」的指引，而非裸错误——降低重试轮数；
  5. **RRF 双路检索用于角色证据检索**：语义（引语/场景相似度）+ BM25（角色名精确命中）融合，正好覆盖「模糊指称」与「精确人名」两类查询；
  6. **卡死检测 + 轮次预算警告**：Arbiter 循环的现成护栏（防无限取证）；
  7. 诚实评价：单人项目、无大规模生产验证，主仓删除本身是维护性风险信号——**借鉴机制吃透后自己实现，不要依赖其代码**；但其「DeepSeek 坑密度」是所有调研对象里最高的，对我们这种同栈项目的单位价值超过大厂项目。
- **近名项目辨析**：用户最初写作「luckycodex」，实为两个不同项目——luckycode（= LuckyD Code，本节）与 **lazycodex**（https://github.com/code-yeongyu/lazycodex ，MIT，OmO 的 Codex 发行版，「LazyVim for Codex」；克隆通读过 README）。lazycodex 顺带发现的三条可借鉴：① 按任务类别路由模型档位（`quick`→mini / `ultrabrain`→高推理，配额纪律与我们「reasoning 只给 Sleeper/Arbiter」同原则互证）；② `$ulw-loop` 的完成判定是 **Oracle 依据证据验证**而非模型自述完成（对应我们「带证据行号才算有效标注」）；③ Librarian 专职记忆管理员 ≈ 我们的 Sleeper。

### 3.12 生态全景（一句话带过，防止「只看一两个」的批评）

2026 年 agent 工具确实井喷，除上述外还有：OpenAI Agents SDK（handoff/session/tracing，https://github.com/openai/openai-agents-python）、Gemini CLI→Antigravity、Aider（git-native）、Cline/Kilo/Roo（IDE 形态，Cline 的 auto-compact 与 Memory Bank）、Goose（扩展机制）、Qwen Code（中文生态）、Ruflo（swarm harness）、BMAD/CrewAI/LangGraph/AG2（编排框架层）。**框架层（LangGraph/CrewAI 等）全部排除**：我们的编排是固定流水线 + 少量分支，确定性 Python 比 DSL 更可调试（MAST 的教训正是框架层协调失败难归因）；**CLI harness 层**（Codex/OpenCode/Claude Code/DSH）借鉴机制而非引入代码，因为它们的核心复杂度在沙箱/权限/编辑器，与我们的任务无关。筛选逻辑：只抄「与长会话多轮 + 上下文管理 + 隔离裁决」有关的零件。

## 4. Agent 角色分工总表

| # | 角色 | 形态 | 任务 | 上下文策略 | reasoning | 频次/卷 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | Orchestrator | 纯 Python | 流水线调度、分歧检测、checkpoint、合并 | — | — | 常驻 |
| 1 | Ledgerist | 单次 LLM | 通读整卷产角色账本（canonical+别名+揭示行号） | 整卷一次读（~9.5 万 tok） | none | 1 次 |
| 2 | Labeler-A 整卷证据 | 单次 LLM | 整卷强制引用标注（现 evidence_annotate） | 整卷一次读 | none | 1 次 |
| 3 | Labeler-B 连续多轮 | 滚动会话 | 逐条标注+交替追踪（现 cont_agent） | 滚动 + 分层压缩（§7） | none | ~1400 轮 |
| 4 | Labeler-C 场景块 | 每块新会话 | 场景对齐的批量标注（新视角） | 每块 ~2-3K 行 + 全局账本 + 全局锚点 | none | ~40-60 块 |
| 5 | Sleeper 睡眠整理 | 后台 continuable | 异步重整账本/锚点/场景摘要（Letta 式） | 自有会话，读写记忆层 | **high** | 异步持续 |
| 6 | Arbiter 裁决器 | one-shot 子代理（批量会话） | 分歧条目受限选择+证据核验 | fresh：账本+候选+证据+工具 | **high** | ~10-15 会话 |
| 7 | Normalizer | 代码+小 LLM | 泛称归一、空标签兜底、身份消解 | 小上下文 | none | 少量 |

要点：

- **A/B/C 三个 pass 是三种正交视角**（信息结构不同，不是采样不同）。C 是新增的关键视角：场景对齐（用旧系统 scene mapper 的思想做纯代码切分）+ 块内全量文本 + 全局账本，粒度介于「整卷」与「逐条」之间——这直接对应 SWE-agent 的窗口消融（30 行太小、全文件太大、100 行最优，我们的对应物是「块」）。
- **Sleeper 与 Arbiter 是仅有的两个开 reasoning 的角色**：它们调用量小、任务聚焦（「不受延迟约束」的 Letta 洞察 + 我们平台「批量必须关推理」的约束正好兼容）。这两个角色如果 reasoning 也不行，那才轮到质疑模型能力——目前的证据还没到那一步。
- **没有「审阅者」角色**。旧系统的全部审阅类机制（scene-review、陪审、反证）在新架构里被「分歧检测 + 受限裁决」取代：只看两/三 pass 不一致的条目，且只能从候选中选，不能自由改写。这同时规避了「审阅器信息少却有改写权」（净改坏 174）和「误差不可逆传导」（v6）两个已付学费的坑。

## 5. 工具接口设计（ACI 四原则的应用）

工具集（对 Labeler/Arbiter 开放，各角色白名单不同）：

| 工具 | 签名 | 设计理由（对应 ACI 原则） |
| --- | --- | --- |
| read_lines | `(start, count≤60)` → 带行号原文 | 已有。有界输出（紧凑）；行号锚定（反馈可核验） |
| search_name | `(name)` → 该名字出现的行号列表（≤30 个，含前后各 1 行摘要） | **汇总式搜索**（SWE-agent：返回命中位置而非全文 +6pp）。取代旧系统「身份搜索」的任意 grep |
| dialogue_window | `(D编号, radius)` → 相邻引语序列 + 本地各 pass 的标注 | 给 Arbiter 看「交替结构」（多轮 pass 的独对来源），紧凑呈现 |
| ledger_lookup | `(name)` → canonical、别名、首次出场行、揭示行 | 记忆层的只读检索口；反馈含「为什么归并」 |
| ledger_propose | `(alias, canonical, evidence_line)` | 只提议不直接写（写入由 Sleeper 异步核验合并——ADD-only + 检索时排序，Mem0 式） |

护栏（guardrails）：

1. **解析器白名单**：沿用 strict_parse + 黑名单（编号、提示词、标点），外加「候选集约束」——Arbiter 的输出必须在候选集合 ∪ 账本名内，否则视为无效重试（防「说话人」类污染重演）；JSON 修复采用 LuckyD Code 的 `_repair_json` 方式——**所有修复只在字符串字面量之外进行**（逐字符跟踪 in_string 状态），删尾逗号、补未闭合括号，不破坏含特殊字符的合法值；
2. **每条 user 消息重复输出格式约束**（长会话格式漂移的既有教训，OpenCode reminders 同款）；
3. **工具结果头尾修剪**：超 8K 字符的 read_lines/search 结果保留头 4K+尾 1K + 标记（DSH tool-result-pruner 与 LuckyD Code `_truncate_tool_result` 双重互证，后者参数为 8000=头 4000+尾 2000），原始全文留在事件日志可回放；
4. **证据行号强制**：所有标签必须带证据行号，无证据=无效（这是已被消融证明的唯一「不破坏正确项」的机制，扩展到所有 pass 和 Arbiter）；
5. **循环护栏**（LuckyD Code 同款）：卡死检测（连续 3 次相同「工具+参数」哈希 → 注入打破消息）+ 轮次预算警告（Arbiter 剩 ≤2 轮取证时注入收尾指令，标志位防重复）；解析失败反馈自带 fix_hint（「怎么改」的指引而非裸错误）。

## 6. 时间预算与量化预期

单卷预算分配（对照 12h 上限）：

| 阶段 | 预计耗时 | 说明 |
| --- | ---: | --- |
| Ledgerist + Pass A | ~5 min | 已有 |
| Pass B（连续多轮） | ~3.5h | 已有实测 |
| Pass C（场景块） | ~1-1.5h | 块数少、每块一次调用为主 |
| Sleeper | ~0（异步搭车） | 与 B/C 并行 |

| **合计** | **~7.5-9h** | 留 25-40% 余量给重试与限流退避 |

注意并发与限流：本地池 20 账号，B、C 分散在不同账号上并行（此前五卷并行才触发 cooldown，单卷双 pass 应安全）；Arbiter 串行跑避免和 pass 抢配额。

95% 的达成路径（重申 §1 公式）：

- **关键参数 = Arbiter 在分歧条上的命中率 A**。校准方法：先在卷 1 的分歧子集上离线测 A（评分只在开发侧，不进运行时，不违反不泄露约束）。A≥0.70 再铺满五卷；A<0.60 则说明 v4-flash 连受限裁决也不够，届时「模型能力论」才有充分证据。
- **正在跑的 refine_divergent.py 就是 A 的第一次测量**。建议把它从「重标」改成「受限选择」再测一次：只给候选+证据做二选一，预期显著高于自由重标（受限消除了格式与输出空间噪声）。
- 盲区 r：C pass + 专职判定制造分歧后同样走 Arbiter；对 r 的期望放到 0.05-0.15（203 条里旧系统 0 对，是全任务最硬的骨头，不要指望它）。

## 7. 上下文压缩设计（分层）

原则（综合 Codex/OpenCode/Claude Code/DSH 四家实现的共识）：**便宜的先来、原子上不破坏、原始数据永不丢、蒸馏是最后手段**。

对 Labeler-B（唯一的长会话角色）：

| 层 | 手段 | 成本 | 触发 |
| --- | --- | --- | --- |
| L0 | 事件日志全量落盘（JSONL：每轮消息+工具调用+结果+usage） | 0 | 每轮 |
| L1 | 工具结果修剪：保留最近 3 次完整，更早的替换为占位符 | 0 | 每次调用前 |
| L2 | 旧轮裁剪：按「完整问答对」整块删除（保持 tool_call/tool_result 配对），保护最近 20 条锚点 | 0 | prompt_tokens > 400K |
| L3 | 蒸馏：handoff 式结构化摘要（账本 + 场景进度 + 关键判决与依据 + 待办），替换全部历史，重注入系统提示 + 账本 + 锚点 | 1 次调用 | prompt_tokens > 600K（现有阈值保留为 L3 触发线） |
| L4 | 应急截断：API 报超长时丢最旧 20% 轮次重试（Claude Code PTL 同款） | 0 | 仅异常 |

相比现状的改进：现在 600K 之前什么都不做、到了一刀切全蒸馏——L1/L2 的存在让 L3 触发次数减少，每次蒸馏之间的「信息真空期」变短；蒸馏提示词从「账本 JSON」升级为 handoff 文档（Codex 同款四段式），保留场景/判决/依据等结构化状态而不只是人名表。

对 Labeler-C：每块新会话，无压缩需求（块内 ~2-3K 行 << 1M）。
对 Arbiter：每会话 fresh，工具结果即时修剪（L1）即可。

**token 计数口径**：继续用最后一次调用的 `usage.prompt_tokens` 覆盖式更新（已有的正确做法，与 OpenCode 用缓存计入口径一致），L2/L3 阈值判断基于它。

## 8. 记忆层设计（三层 + sleep-time）

| 层 | 存储形态 | 谁写 | 谁读 | 借鉴 |
| --- | --- | --- | --- | --- |
| Core（常驻上下文） | 角色账本（canonical/别名/揭示行）+ 最近 20 锚点 + 当前场景指针 | Sleeper | 所有 agent | Letta core memory blocks |
| Episodic（会话内） | 每条标注记录：D编号、标签、证据行、理由、置信标记；按场景聚合的摘要 | 各 Labeler 自动 | Sleeper、Arbiter（经 dialogue_window 工具） | DSH append-only 事件日志 |
| Archival（归档） | 全量轨迹 JSONL（含所有工具调用与结果原文） | Orchestrator | 只被工具按需检索（回放/归因用） | DSH spill + 回放 |

写入语义：**ADD-only**（Mem0 式）——账本合并提议（ledger_propose）不直接生效，由 Sleeper 核验后追加为新版本条目，检索时按 recency + 证据强度排序；错误合并可回溯。这直接针对泛称归一/别名归一两次失败的根因（破坏性合并在写入时就把错误固化）。

Sleeper 的工作清单（对应 Letta sleep-time 的「重整学习上下文」）：
1. 合并别名提议、回填身份揭示（「前文称女孩→后文揭示是赫萝」类的反向标注）；
2. 从 B/C 的 episodic 记录里抽「交替对」模式（A↔B 对话结构）供 Arbiter 用；
3. 维护场景摘要索引（场景号→在场人物→剧情一句话）；
4. 冲突登记：同一条目两个 pass 证据行冲突时，把冲突也写进 Episodic（给 Arbiter 的输入里显式呈现「冲突在哪一行」——Sample-Scrutinize-Scale 的「比较即信号」）。

## 9. 反模式清单（每条都有已付学费的对应实验）

1. ❌ 触碰共识区（任何形式的「再核一遍」）——回归率 99.21% 的资产不容赌；
2. ❌ 同 prompt 投票/温度采样——相关性失败，两次实测；
3. ❌ 给审阅器自由改写权——信息少的角色只能选择不能创作（v6/7-16/7-26 三次学费）；
4. ❌ 用 LLM 做协调/调度——MAST：41.8% 失败在规格与协调层；
5. ❌ 写入时破坏性合并记忆——归一两次净负的根因；
6. ❌ 批量任务开 reasoning——平台实测烧光预算（390s 完成 152/1459）；
7. ❌ 长会话只在爆窗时一刀切压缩——分层先行；
8. ❌ 解析 fallback 接受任意短字符串——D 编号 bug 与「说话人」污染；
9. ❌ 为「通用性」引入编排框架（LangGraph/CrewAI 等）——固定流水线用确定性 Python，可调试性即正确性；
10. ❌ 继续加「第 N 层审阅」堆复杂度——17K 行的旧系统就是这条路终点，业界 correlated-failure 研究证明这条路在数学上就不通。

## 10. 工程落地建议（防再次膨胀）

1. **代码组织**：每个角色一个文件（`agents/ledgerist.py / labeler_cont.py / labeler_scene.py / sleeper.py / arbiter.py / normalizer.py`）+ 共享 `harness.py`（调用、压缩、事件日志、工具执行）+ `orchestrate.py`（流水线）。目标总量 **≤1500 行**——对照：旧系统 12165 行核心 + 4700 行辅助。控制手段：harness 只做四件事（call/compact/log/tool），任何新想法先问「是不是又一层审阅」。
2. **事件日志格式**（DSH 式）：`{seq, ts, agent, role, content, tool_calls, tool_results, usage, checkpoint}` 每卷一个 JSONL；断点续跑从日志重建状态（现在的 ckpt.json 是它的退化版）。
3. **复用清单**：`probe_dsv4flash.py`（调用层）、`evidence_annotate.py`（Pass A）、`cont_agent.py`（Pass B 骨架 + strict_parse + 上下文口径）、`twopass_annotate.py`（Ledgerist）、`identity_resolve.py`（Normalizer 组件）、`refine_divergent.py`（Arbiter 原型，改造为受限选择）。**新增代码主要只有：场景切分、Labeler-C、Arbiter、Sleeper、分层压缩、事件日志**。
4. **验证顺序**（每步都有可回滚的中间产物）：
   - 第 1 步：卷 1 分歧子集上测 Arbiter 受限选择命中率 A（决定整个方案 go/no-go）；
   - 第 2 步：A≥0.70 → 铺满卷 1 全量，对比 92.31 基线；
   - 第 3 步：加入 Labeler-C 与 Sleeper，看盲区 r 与分歧结构变化；
   - 第 4 步：五卷全量 + 时间预算实测（≤12h/卷）。
5. **风险登记**：最大风险是 A 不达标（<0.60）——那将首次给出「v4-flash 编排上限已达」的严格证据，届时应当讨论的不是编排而是模型（用户约束 1 是否放开）；次要风险是 Arbiter reasoning 调用被限流拖长时间——预留串行窗口 + 重试退避。
