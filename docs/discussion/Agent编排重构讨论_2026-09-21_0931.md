## 〇、核心论点（先说结论）

**同意你的判断：当前瓶颈是 agent 编排，不是模型能力。** 证据有三：

1. **时间预算只用了 29%**。单卷预算 12 小时，当前 cont_agent 单卷 ~3.5 小时。也就是说，每条引语的平均计算预算还可以放大 **3.4 倍**（30s/条 vs 当前 8.7s/条），这是纯粹的编排空间，跟模型能力无关。
2. **旧系统用更弱的模型（SenseNova Flash Lite）做到了 94.19%**，且其首遍（93.42%）就高于我们当前终值（92.77%）。同模型下机械的信息组织方式确实能拉开差距——重构准备六已实测证明"逐条深查+工具检索+25轮短记忆+角色状态"的每一部分都不是白费的。
3. **新系统当前方案极简**：`cont_agent.py` 全部 311 行，±8 行窄上下文 + 一个 `read_novel_lines` 工具 + 60 万 token 一次性蒸馏。对比旧系统的信息视角（场景、角色状态、证据库、交替追踪），新系统只保留了"交替追踪（多轮）+ 账本"两个。**编排在信息供给层面远未达到旧系统的水平，更别说超过。**

但要划清一条边界：旧系统的教训同样成立——**加层不等于加信息**。7/16 审计净改坏 46、7/26 场景层净改坏 174，都是"审阅者信息不比标注者多却拥有改写权"的教训。新方案的每一步设计都必须回答："这一步给模型提供了什么**旧视角没有的信息或视角**？"

## 二、源码级发现：三大 harness 的压缩与编排细节

### 2.1 OpenAI Codex：压缩就是"写交接文档"

源码位置：`codex-rs/prompts/templates/compact/prompt.md`（原文）：

> You are performing a CONTEXT CHECKPOINT COMPACTION. Create a handoff summary for another LLM that will resume the task.
> Include:
> - Current progress and key decisions made
> - Important context, constraints, or user preferences
> - What remains to be done (clear next steps)
> - Any critical data, examples, or references needed to continue

压缩后的新对话开头模板（`summary_prefix.md`）：

> Another language model started to solve this problem and produced a summary of its thinking process. You also have access to the state of the tools that were used by that language model. Use this to build on the work that has already been done and avoid duplicating work.

要点：
- 压缩被定义成 **CHECKPOINT（检查点）+ handoff（交接）**，明确写给"下一个接手的 LLM"，包含进度、决策、约束、剩余工作。
- 触发阈值可配置（`model_auto_compact_token_limit`），且有两种计量口径：`Total`（全部上下文）或 `BodyAfterPrefix`（只算前缀之后的增量）——这个设计允许"固定头 + 增长体"的会话只在体增长超限时压缩。

### 2.2 OpenCode：两阶段压缩 + tail 保留 + 链式总结

源码位置：`packages/opencode/src/session/compaction.ts`。关键常量与逻辑：

```
PRUNE_MINIMUM = 20_000    // 可回收量低于 20K token 就不动
PRUNE_PROTECT = 40_000   // 最近 40K token 的工具输出原样保护
TOOL_OUTPUT_MAX_CHARS = 2_000  // 工具输出序列化时截断到 2000 字符
MIN/MAX_PRESERVE_RECENT_TOKENS = 2_000 / 15_000
```

**阶段一 prune（剪枝）**：倒序遍历消息 parts，跳过最近 2 个 user turn，保护最近 40K token 的工具输出，把更老的工具输出标记为 `compacted`（发送给 LLM 时替换成 `[Old tool result content cleared]`），但**调用记录本身保留**（"查过什么"的痕迹不丢）。

**阶段二 summarize（总结）**：溢出触发；专门有一个**隐藏的 compaction agent**（不可被用户选中），可以用与主对话不同的模型。要点：
- **tail 保留**：最近的对话按预算保留原文（默认 `min(15K, max(2K, 25% 可用窗口))`），只总结更早的 head。不是全部蒸成一个摘要。
- **链式总结**：`previousSummary` 会作为输入传入，新总结在旧总结基础上滚动更新。
- **总结的序列化格式**是结构化转写：`[User]: ... / [Assistant]: ... / [Assistant tool call]: xxx(args) / [Tool result]: ...`，保证总结模型看到的是带角色的完整轨迹。
- 溢出兜底：如果压缩后仍然溢出，回退为 **replay 最后一条 user 消息**（丢中间历史但保住任务意图）。

子 agent（`tool/task.ts`）：`background` 参数支持后台子 agent；`task_id` 支持把后续消息发回**同一个子 agent 会话**续聊（不是重新起）；嵌套深度限制（`subagent_depth`，默认 1）；返回格式是结构化 XML `<task id=... state=...><task_result>...</task_result></task>`。

### 2.3 DeepSeek Harness：压缩是事件日志里的事务

源码位置：`packages/compaction/`（一个包族：compaction / compaction-basic / compaction-tool-result-pruner / compaction-image-offload / command-compact）。要点：
- **一切皆插件**：压缩本身是一个能力族，五个包各管一段（自动压缩、手动 /compact、工具输出剪枝、图片卸载、命令入口），通过 Cordis 插件系统组合。
- **压缩事务化**：session 是 append-only 事件日志，压缩以 `compaction/start` / `compaction/end` 事件对提交，压缩期间新增的消息会触发 `SurfaceChangedError`（"总结所依据的边界已经变了"）而拒绝提交——**异步压缩与正在进行的对话之间有一致性保证**。
- **tool-pairing 不变式**（`tool-pairing.ts`）：assistant 的 tool_call 和 tool result 是协议配对，压缩选段时**绝不拆散**，否则 API 直接拒绝请求。
- **retain-tail 预算**：`selectCompactableRange` 保证最近尾部按 token 预算原样保留（与 OpenCode 同思路）。
- 官方 benchmark 目录名本身就说明他们在优化什么：`agent-continuation`（压缩后接续）、`conversation-fold`、`long-session-browser`。

### 2.4 Claude Code（闭源，但有官方 SDK 文档 + 架构论文）

arXiv 2604.14228《Dive into Claude Code》+ 官方文档：
- 子 agent 独立上下文，**只有最终消息回到父对话**；完整轨迹写独立 `.jsonl`（sidechain transcript），不污染父会话。
- 隔离三档：in-process（仅上下文隔离）/ worktree（git 工作树隔离）/ remote。
- 子 agent 无持久记忆——官方推荐的跨运行记忆模式是 **file-based memory**：子 agent 把结论写进结构化文件，下一次任务的输入里带上这个文件路径。
- agent teams 警示：多 agent 团队耗约 **7×** token（plan 模式实测），协调用文件锁 + inbox JSON 文件，不是消息总线。
- 自动压缩在 ~70% 窗口利用率触发（官方 context engineering 指南：60-70% 主动压缩，别等 90%+ 的"腐烂区间"——此时连生成的摘要质量都是降级的）。

## 三、映射到本项目：六个设计决策

### 3.1 Agent 分工：五角色流水线（谁做什么）

先立一条从实测里长出来的**铁律**（三条证据：7/16 同源投票净改坏、7/26 审阅器信息更少却改写、6/16 A/B 拆分后召回 0→91%）：

> **每个角色必须满足以下之一，才有存在价值：(a) 提供 Labeler 没有的信息；(b) 提供不同的信息视角（如"只看反证"）；(c) 改变模型的行为先验（任务分解）。单纯"再看一遍"的同源审阅一律不许上。**

据此设计（**按信息视角分工，不按职责名称分工**）：

| # | 角色 | 输入 | 输出 | 存在理由（对应铁律） | 预估成本 |
| --- | --- | --- | --- | --- | --- |
| 0 | 场景分割器 | 原文行 | 场景块索引（起止行号） | (a) 给所有下游 agent 一个共同的"自然场景"视野；纯规则，零模型调用 | ~0 |
| 1 | 账本构建器 | 整卷 | canonical+别名账本 | 已验证（+账本 91.47% vs 无账本 90.74%）；twopass 已有 | 1 调用/卷 |
| 2 | **场景标注 Agent**（主力） | 当前场景全文 + 账本 + 前情摘要 + 最近锚点 | 场景内每条引语的 `说话人\|证据行号\|理由` | cont 的多轮交替追踪 + 场景级全局视野（新信息） | 见 3.2 |
| 3 | 无人称引语判定 Agent | 整卷 + 引语编号 | 疑似非发言清单（高召回） | **(c) 任务分解**——已实测拆开后召回 0→91%；联合任务里模型行为先验是"每处引语都有人说话" | 1-2 调用/卷 |
| 4 | 分歧裁决 Agent | 两个方案输出 + ±15 行上下文 + 账本 | 改判结果 | (a) 它看的是**两个独立方案的分歧位置**——这个信息任何单方案都没有；且 `reasoning_effort=high` 是唯一没试过的模型杠杆 | 仅 ~731 条分歧 |
| 5 | 身份消解 Agent | 实际输出词表 | 别名归并映射 | 已验证 +0.19pp（v2 +1.19）；专注小任务对别名敏感 | 1 调用/卷 |

注意三点：
- **旧系统的场景 Mapper / Investigator / 镜像陪审全部不上**。它们的净收益实测为负（−174 / −46），且违反铁律 (a)。
- 角色 3 的输出**不直接改写**主标注结果，只作为"复核名单"进入角色 4 的视野（精确率只有 49%，直接改写会重演 6 月份的过判）。这是对"版本 6 三阶段流水线失败"的修正：A/B 判定**从串行的前置门，改为并行的证据源**，误差不可逆传导就不存在了。
- 角色 4 裁决的合法输入是"两方案输出对比"（定位不用答案，refine_divergent.py 已实现此逻辑），不违反"不泄露答案"约束。

### 3.2 一次处理多少：场景块为基本单元

三个候选粒度的实测证据：

| 粒度 | 实测 | 问题 |
| --- | --- | --- |
| 整卷一次读 | 91.47%（evledger） | 无人称引语欠检测（联合任务行为墙）；实名互换段弱 |
| 逐条（±8 行） | 92.31%（cont） | 场景切换处丢全局身份；窄上下文丢全卷消歧信息（准备六：D201-300 仅 26%） |
| 每幕分块 | 88.69%（act，v5） | 幕太大且边界武断 |
| 60 条硬切块 | 失败（v7） | 粗暴丢弃上下文 |

**没有一个试过"自然场景块"。** 旧系统 7/26 的失败恰恰是因为"场景"被收紧到最多 6 句、补边仅 6 行——**不是自然场景**（复盘原话："并不是真正自然场景"）。而真实阅读中，说话人归属的消歧信息几乎全部来自场景内（谁在场、谁刚说话、对话主题）。

建议：
- **基本单元 = 自然场景块**：以空行 + 场景切换信号（时间词、地点词、视角切换）做确定性切分，可先按"空行为主、目标每块 10~40 条引语"调参。切分本身零模型调用，纯 Python。
- 场景内**逐条多轮**（保留 cont 的交替追踪能力），但每条的上下文是**整个场景**而非 ±8 行——场景内全局视野是新增信息。
- 场景间传递：账本 + 前情摘要 + 最近锚点（见 3.4）。
- 兜底：对账本中"该场景在场人物 < 2 且引语 > 5"的块，自动并入相邻块。

### 3.3 每个角色的多轮对话上下文设计

| 角色 | 会话结构 | 上下文构成 | 依据 |
| --- | --- | --- | --- |
| 场景标注 Agent | **每场景一个滚动对话**（场景内逐条多轮） | system（任务+格式铁律）→ 账本（结构化注入）→ 前情摘要 → 最近 8-10 条锚点 → 本场景原文（带行号）→ 逐条问答 | Claude Code 子 agent 模式：干净上下文 + 最小充分信息；场景结束即弃，无需压缩 |
| 无人称判定 Agent | 单次调用（整卷） | 整卷原文 + 引语编号清单 → 输出疑似清单 | 已实测该任务形态下召回 91% |
| 分歧裁决 Agent | 每条一次独立调用 | ±15 行原文 + 账本 + 前后已标 ±5 条 → reasoning high | refine_divergent.py 现有结构 |
| 账本/身份消解 | 单次调用 | 各自的专注输入 | 已有实现 |

关键变化：**压缩的负担大幅下降**。当前 cont_agent 要在 1M 窗口里滚完一整卷（1459 条），60 万 token 时蒸一次；改成场景会话后，每个会话只有"一个场景 + 固定头"，平均几千到几万 token，**大多数场景根本触不到压缩**。压缩只发生在"超长场景"（比如 50+ 条引语的场景需要场景内中途压缩）。这正是 OpenCode/dsh 的做法：子 agent 短会话天然规避压缩，压缩是兜底不是常态。

### 3.4 记忆层：三层结构，全部带行号可回查

借鉴 Letta 的 core/recall/archival 分层 + Anthropic 的 structured note-taking + 旧系统 EvidenceVault 的教训（"记忆把旧猜测升级为事实"），设计：

| 层 | 内容 | 生命周期 | 写入者 |
| --- | --- | --- | --- |
| **L1 账本（core）** | canonical 名 + 别名 + 身份揭示事件（如"女孩=赫萝，L1234 揭示"） | 全卷持久，边标边更新 | 场景标注 Agent 每场景结束时提交增量 |
| **L2 前情摘要（recall）** | 已完成场景的情节流（每场景 1-3 句：谁在场、发生了什么、身份变化） | 全卷持久，滚动拼接 | 场景标注 Agent 场景结束时生成 |
| **L3 锚点（working）** | 最近 8-10 条标注结果 `D####\|说话人` | 滑动窗口 | 主控 Python 维护 |

规则（对应复盘文档 9.1 "防止记忆把旧猜测升级为事实"）：
1. **记忆只存"原文可回查的事实"**：账本条目必须带行号引用；摘要里的人物动作必须是原文出现过的。写入时由 Python 校验行号在合法范围内，不做语义校验（语义校验是又一个同源审阅，违反铁律）。
2. **L2 拼接到一定长度（如 40 个场景）做一次压缩**：用 Codex 式 handoff 提示词蒸成"前情梗概"（保留身份变化和未决悬念，丢弃过程细节）。这是全卷唯一需要 LLM 参与的记忆压缩，频率低。
3. **不引入向量检索 / 图谱记忆**。mem0/Zep 那套是为"跨会话个性化记忆"设计的；本任务是单卷批处理，账本+摘要+锚点的确定性结构更可控，也符合你"不要臃肿"的要求。hermes-agent 的 FTS5 历史检索思路可以用一个 20 行的"按角色名查行号索引"替代（见 3.5）。

### 3.5 工具调用：给标注 Agent 配三个只读工具

Anthropic 的 just-in-time 原则：上下文里只放轻量标识（行号/名字），正文按需加载。当前 `read_novel_lines` 保留，新增两个：

```json
{"name": "read_novel_lines", "start": int, "count": int}   // 已有，count 上限 60
{"name": "search_name", "name": str}                        // 新增：返回该人名/泛称出现的所有行号（倒排索引，Python 预建，零模型成本）
{"name": "read_scene", "scene_id": int}                     // 新增：返回整个场景原文（跨场景回查时用）
```

设计要点：
- `search_name` 解决跨场景身份链接（"这个名字上次出现在哪、以什么身份"），这是旧系统身份搜索层的有效部分，用倒排索引实现只要几十行 Python，无模型调用。
- **工具结果永不进入 L1/L2 记忆**（OpenCode prune 的精神）：工具输出在场景会话结束后随会话一起丢弃，只有"说话人|证据行号"结论进入 L3 锚点。这从结构上杜绝了旧系统"证据库越滚越大"的问题。
- 输出格式的解析沿用 `strict_parse` + 黑名单（D 编号、提示词污染那两个 bug 的教训），每条 user 消息重复格式约束（长会话格式漂移的教训）。

### 3.6 上下文压缩：三道防线，阈值前移

当前方案的问题：60 万 token（1M 的 60%）一次性把全部历史蒸成账本，**丢掉了情节流和场景上下文**——而复盘里"全卷消歧信息"恰恰是逐条窄上下文缺的东西。改成场景会话后压缩需求大降，但仍保留三道防线（全部来自源码验证过的做法）：

1. **防线一（场景会话内，超长场景才触发）**：超过阈值（建议 30 万 token，即 1M 窗口的 30%——比 60-70% 共识更激进，因为我们的会话短、触发即说明场景异常长）时，用 **Codex handoff 模板**蒸历史，**保留当前场景原文 + 最近 5 轮问答**不蒸（OpenCode tail 保留 25% 的思路，我们场景会话里"当前场景原文"就是必须原样保留的 keep-verbatim 区）。
2. **防线二（L2 前情摘要滚动压缩）**：见 3.4 规则 2。
3. **防线三（溢出兜底）**：压缩后仍溢出 → 回退 replay 当前场景（重读场景原文 + 已有结论），丢弃中间问答（OpenCode 的 overflow replay 思路）。

**阈值与计量的工程约定**（延续现有正确做法）：上下文占用一律用 API 返回的 `usage.prompt_tokens`（最后一次调用的值，覆盖式），压缩触发判断也用它，不自算 token。

## 四、时间预算核算（单卷 ≤ 12 小时）

以最难的卷（v4，1561 条）估算。场景标注 Agent 单条成本参考 cont 实测（~8.7s/条，含多轮+工具），场景会话固定头（账本+摘要+场景原文）使单条略慢，按 12s/条计：

| 阶段 | 条数/调用量 | 单价 | 小计 |
| --- | --- | --- | --- |
| 场景分割 + 倒排索引 | 0 模型调用 | — | ~0 |
| 账本（twopass 已有） | 1 调用 | ~90s | 1.5 min |
| 场景标注（主力） | 1561 条 | ~12s/条 | **312 min** |
| 无人称判定 | 1-2 调用（整卷） | ~300s | 10 min |
| 分歧裁决（reasoning high） | ~731 条 × ~2 信号对比 | ~8s/条 | 58 min |
| 身份消解 | 1 调用 | ~60s | 1 min |
| **合计** | | | **~6.4 小时** |

余量 ~5.6 小时（46%），可用于：超长场景的重试、模型服务波动的等待、以及（如果首轮实测有正收益）把分歧裁决扩展到"分歧 + 高风险"全集。**五卷并行时受本地模型池限流影响会拉长，但单卷预算依然成立**（单卷跑能到 ~13 条/分钟的实测基准）。

## 五、预期收益与风险（诚实估计）

### 有实测支撑的部分

| 机制 | 实测增益 | 在新方案中的形态 |
| --- | --- | --- |
| 多轮交替追踪 | 难卷 +3.4/+4.4pp | 场景会话内逐条 |
| 强制引用证据 | +2.51pp（回归率 99.21% 的保护机制） | 输出格式保留 |
| 账本 | +0.73pp | L1 |
| 身份消解 | +0.19pp | 角色 5 |
| A/B 任务分解 | 非人物召回 0→91% | 角色 3（并行证据源，非前置门） |

### 假设待验证的部分（按风险从低到高）

1. **场景级上下文替代 ±8 行**（低风险）：与"逐条 vs 整卷互补"的既有结论同向，且修复的是已知弱点（场景切换丢身份）。
2. **分歧裁决 + reasoning high**（中风险）：分歧定位本身是净信息（两方案独对 395/336 的不对称），但裁决者仍是 v4-flash，对 203 条共同盲区无能为力——它们两个方案都错，根本不产生分歧信号。
3. **无人称判定作为并行证据**（中风险）：49% 精确率意味着清单里有大量误报，裁决层需要设计好"证据权重"（建议：仅当裁决 Agent 也独立倾向非人时才改判，即两个不同视角同向才动）。

### 对 95% 目标的量化分解

从 92.77% 到 95% 需要净修 **156 条**（7009 × 2.23pp）。可获得的空间：
- 分歧 731 条中，多轮独对 395 / 整卷独对 336，若裁决把"信对的一方"的正确率从当前的隐式 54%（395/731）提到 75%，净增 ~145 条 —— **这一项如果做成，几乎够到 95%**。
- 203 条共同盲区：任何 v4-flash 内部编排都无法产生新信号（三方案 0 对）。唯一未试的杠杆是 `reasoning_effort=high` 的深推理（refine_divergent 正在做的事），如果有效，另有 ~50-100 条空间；无效则确认是模型边界。
- 结论：**场景化 + 分歧裁决是冲击 95% 的主路径；共同盲区是 reasoning 杠杆的试验田；两者叠加后仍不足，才轮到讨论换模型。**

### 必须防的坑（旧系统教训的直接映射）

1. 每个新机制先在**分层实验集**（重构准备二已建）上消融，无正净收益不进默认路径。
2. 裁决 Agent **只对分歧条目工作**，绝不对"两方案一致且正确率高"的大盘动手（6987/7009 保留基线的止损教训）。
3. 场景切分参数不许按五卷调到过拟合（复盘 6.8：防对五卷过拟合），留出未参与调参的场景做 holdout。
4. 所有组件保持"可关闭"：每个角色一个独立开关，坏了就退回上一级基线，不许再有不可回退的永久主流程。

## 六、与"直接用现成 harness 跑"路线的关系

调研前你提过一个假设：成熟 agent 工具 + 强模型可能比自研更准更快。源码看下来的结论：

- **直接套用不划算**。Codex/OpenCode/dsh 的复杂度都在"编码工作流"（文件编辑、沙箱、权限、diff 审查）上，与标注任务无关；它们的核心可复用件（压缩、子 agent 会话、工具循环）在我们的场景里每个只有几百行 Python 的等价物。
- 但**设计模式应当照抄**：本方案 3.3-3.6 的每个设计都能对应到源码里的验证过的做法（handoff 模板 / tail 保留 / tool-pairing / file-based memory / 70% 阈值 / 结构化总结输出）。这就是"不重复造轮子"的正确姿势——**借设计，不借代码**。
- 如果未来这个项目要扩展成通用长文档标注平台，dsh 的"一切皆插件"结构值得回来再看；当前单任务阶段，一个 1500 行以内的干净流水线比插件框架更可维护。
